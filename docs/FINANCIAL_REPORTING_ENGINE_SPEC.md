## 1. الملخص التنفيذي

وردة تمتلك أساسًا محاسبيًا قابلًا للبناء عليه، لكن التقارير الحالية ليست محرك تقارير موحدًا: منطق العرض موزع بين خدمات وجداول وRPCs ومسارات بديلة غير متكافئة، وبعض التجميع يجري في المتصفح.

والأخطر أن **القوائم المالية اليوم لا تعرض بيانات فعلية**: خدمة القوائم تفشل في مطابقة **20 من 20** سطرًا في دفتر الأستاذ، فتُخرِج قائمة دخل وميزانية صفرية «متوازنة» — وهو بالضبط فخ الصفر المعقول (`0 = 0`). السبب المباشر ليس عمودًا legacy، بل **انقطاع ترميز الحسابات التاريخية عن شجرة الحسابات القانونية** (F-13).

> **الترتيب التنفيذي الملزم:**
> 1. **متوازيان:** (أ) **Migration 153** — ترحيل المبالغ الميكانيكي والقيود والدقة؛ يبدأ فورًا ولا يحتاج قرارًا محاسبيًا. (ب) **قرار Mapping/Quarantine** للأكواد التاريخية (ADR-FR-014/015).
> 2. **FIN-REP-000 يُغلق بـMigration 154** — الشجرة القانونية والـFK وتطبيق Mapping — **ولا تبدأ قبل اعتماد القرار في 1(ب)**.
> 3. عزل الأبعاد وأساس الأبعاد (155–156).
> 4. المصدر القانوني الموحد (157).
> 5. محرك القوالب والبذور وحكمها (158–160).
> 6. الواجهة والتصدير، ثم التدفقات والمطابقات، ثم الأداء.

| الأولوية | المجال | النتيجة المطلوبة |
|---|---|---|
| **P0-BLOCK** | قرار محاسبي | Mapping معتمد لكل كود تاريخي، أو ADR حجر موثّق بأثر تدقيقي. يحجب 154 لا 153. |
| P0-0 | تصحيح طارئ | عقد أعمدة قانوني موحد + شجرة قانونية + FK؛ لا سطر posted بلا حساب قانوني. |

| P1 | محرك التقارير | قوالب وأسطر وقواعد وصيغ وRPC موحدة مع حكم بذور. |
| P2 | الواجهة والتصدير | فترات ومقارنات وتوسيع وDrill-down وExcel/PDF. |
| P3 | التدفقات والمطابقات | Cash Flow غير مباشرة ومطابقات GL مع الدفاتر المساعدة. |
| P4 | الأداء | أرصدة دورية مجمعة وحدود زمنية على بيانات حجمية. |

### 3.2 الأثر الحالي المثبت — حسابيًا

`fetchAccountBalances` تقرأ `gl_entry_lines` بفلتر `org_id` وحده (لا فلتر حالة — هذا F-01)، فتقرأ العشرين سطرًا كلها، ثم تطابق كل سطر بـ`account_code` مقابل `gl_accounts.code`:

```
16 سطرًا posted  → كود رباعي غير موجود في الشجرة  → غير مطابق  (F-13)
 4 أسطر  draft   → account_code = NULL              → غير مطابق  (F-10)
─────────────────────────────────────────────────────────────────
20 من 20 غير مطابق ⇒ خريطة الأرصدة فارغة ⇒ قوائم صفرية
```

فالشاشة تعرض قائمة دخل وميزانية صفرية، وتحقق `الأصول = الخصوم + حقوق الملكية` بصيغة `0 = 0`، مع «ملاحظة شفافية: 20 سطر لا يطابق شجرة الحسابات».

**وللمال موضعان معاكسان — وهذا جوهري لتصميم 153/154:**

| | الأسطر المرحّلة (16) | الأسطر الحديثة (4) |
|---|---|---|
| الحالة | `posted` | `draft` |
| `account_id` | NULL | معبّأ (يطابق `gl_accounts`) |
| `account_code` | كود رباعي مجهول | NULL |
| **الأعمدة القانونية** `debit/credit` | **0.00 / 0.00** | 20,987.00 / 20,987.00 |
| **الأعمدة legacy** `debit_amount/credit_amount` | **19,910.00 / 19,910.00** | 0.00 / 0.00 |

فالتحول إلى الأعمدة القانونية (ADR-FR-011) **لا يكفي وحده**: لو حُوِّلت القراءة اليوم إلى `debit/credit` لقرأ التاريخ المرحّل **صفرًا**. لذلك يلزم عملان **منفصلان في طبيعتهما**، ولا يجوز خلطهما:

1. **ترحيل المبالغ — ميكانيكي وآمن:** نسخ داخل الصف نفسه من legacy إلى القانونية. حتمي، بلا تفسير، وقابل للإثبات بحفظ المجاميع. الأسطر الستة عشر **كلها** legacy-shaped قطعًا (`account_id IS NULL` والقانونية = 0 وlegacy > 0)، فلا التباس.
2. **ربط الحسابات — قرار محاسبي:** الكود الرباعي ← الحساب السداسي. **غير قابل للاستنتاج** (ADR-FR-014).

### 3.3 النتيجة الملزمة

- **لا توصف القوائم الحالية بأنها مكتملة أو موثوقة.** لقطة شاشة ناجحة أو مجموعة اختبارات خضراء ليست دليل صحة (F-09).
- **F-13 هو حاجز Migration 154**، وحلّه قرار محاسبي لا هندسي. ولا يحجب Migration 153 لأن ترحيل المبالغ ميكانيكي مستقل.
- **F-10 حرج بنيويًا لا ماليًا اليوم.** لا يجوز التعبير عن أثره بمبلغ مفقود من قوائم صحيحة.
- **الأسطر الرباعية المرحّلة يُرجَّح كونها بيانات Demo** — مؤسسة واحدة اسمها `Default Organization`، وأكواد لا تنتمي لشجرتها. هذا **ترجيح يستوجب تأكيدًا محاسبيًا**، لا أساسًا لتصرف تلقائي. وأيًّا كانت النتيجة **لا تُحذف** (القاعدة الذهبية في `CLAUDE.md`).

| ADR-FR-011 | الأعمدة القانونية | `account_id` و`debit` و`credit` قانونية. `account_code` و`account_name` و`debit_amount` و`credit_amount` أعمدة توافق انتقالية، **يُمنع** استخدامها في أي حساب مالي جديد. |
| ADR-FR-012 | عزل الأبعاد | الأبعاد تعزل بـ`org_id` وحارس المؤسسة النشط؛ نمط `app.current_tenant_id` **محظور**. |
| ADR-FR-013 | نهائية الفترة | `permanently_closed` للقراءة فقط: يُمنع الترحيل والتعديل وإعادة الحساب بأثر رجعي إلا بإجراء إعادة إفصاح مُعتمد منفصلًا. |
| **ADR-FR-014** | **Mapping الأكواد التاريخية** | ربط الأكواد التاريخية بالحسابات القانونية **قرار محاسبي معتمد لكل كود على حدة**، بدليل ومعتمِد مسمّى. **يُمنع** الاستنتاج الآلي أو التخمين بالتشابه أو بالبادئة أو بالطول. لا يُنفَّذ أي **ربط حسابات** قبل اعتماد السجل، ولا تصبح `account_id` إلزامية تاريخيًا قبله. ولا يشمل هذا المنع ترحيل المبالغ داخل الصف، فهو ميكانيكي ومستقل. |
| **ADR-FR-015** | **حجر البيانات غير القانونية** | إن ثبت محاسبيًا أن قيودًا تاريخية بيانات Demo أو غير قانونية، **لا تُحذف ولا تُعدَّل**: يصدر ADR يحدد آلية حجرها (عكس قانوني موثق أو علم استبعاد صريح مع أثر تدقيقي)، وتُستبعد من الرصيد الافتتاحي والتقارير بقاعدة معلنة وقابلة للفحص. |
| **ADR-FR-016** | **التاريخ القانوني** | `entry_date` هو **التاريخ المحاسبي** الذي يحدد الفترة والقوائم. `posted_at` وقت تنفيذ الترحيل **لأغراض التدقيق فقط**. **يُمنع** استخدام `posted_at::date` بديلًا عن التاريخ المحاسبي — قيد يُرحَّل 1 أغسطس بتاريخ محاسبي 31 يوليو ينتمي إلى يوليو. **لا يُضاف عمود `posting_date`** إلا بـADR مستقل يبرّر الحاجة. |
| **ADR-FR-017** | **الفترات بيانات مؤسسة** | `accounting_periods` بيانات **org-scoped** مصدرها Onboarding المؤسسة، **لا** بيانات نظامية عامة، فلا مكان لها في `system_reference_manifest.yml` بـ`org_id IS NULL`. ويرفض المحرك العمل لمؤسسة بلا فترات بعد تفعيل العلم، أو يوفّر Onboarding ذريًا ينشئ السنة المالية وفتراتها. |

### 4.1 قرار الانتقال إلى الأعمدة القانونية

الانتقال **لا يبدأ بربط الحسابات**. والتمييز بين عملين مختلفَي الطبيعة ملزم:

| العمل | الطبيعة | الموضع |
|---|---|---|
| نسخ المبلغ legacy ← القانونية **داخل الصف** | **ميكانيكي وحتمي**، قابل للإثبات بحفظ المجاميع | Migration 153 |
| ربط الكود الرباعي بحساب سداسي | **قرار محاسبي**، غير قابل للاستنتاج | قرار قبل 154 |

الترتيب الملزم:

#### المرحلة صفر — قرار محاسبي حاجز (قبل Migration 154؛ لا يحجب 153)

يُنتَج سجل Mapping معتمد، صفٌّ لكل كود تاريخي:

| الكود التاريخي | الحساب القانوني (سداسي) | المعالجة | الدليل | المعتمد بواسطة | التاريخ |
|---|---|---|---|---|---|
| `1120` | | Mapping / Quarantine | وصف القيود والمستندات المصدرية | | |
| `1130` | | | | | |
| `1161` | | | | | |
| `2101` | | | | | |
| `2162` | | | | | |
| `4001` | | | | | |
| `5001` | | | | | |

قواعد ملزمة:
- كل كود يُحسم صراحةً: **Mapping** إلى حساب سداسي واحد، أو **Quarantine** وفق ADR-FR-015.
- كود بلا حسم = **حاجز**؛ لا تُنفَّذ 154 ولا تُغلق FIN-REP-000.
- يُمنع الاستنتاج الآلي (ADR-FR-014). التطابق العددي الجزئي (`1120` ≈ `112000`) **ليس** دليلًا.
- السجل يُحفظ في المستودع بجانب migration 154 ويُشار إليه في runbook التطبيق.

#### Migration 153 — المبالغ والقيود والدقة (**بلا ربط حسابات**)

> التمييز الحاكم: **ترحيل المبالغ ميكانيكي فيجوز هنا؛ وربط الحسابات قرار محاسبي فيُمنع هنا.**

1. **ترحيل المبالغ** من legacy إلى القانونية داخل الصف نفسه، **مقيَّدًا بشرط صريح** لا يلمس غيره:
   ```sql
   WHERE account_id IS NULL AND debit = 0 AND credit = 0
     AND (debit_amount > 0 OR credit_amount > 0)
   ```
   يشمل اليوم 16 صفًا بمجموع `19,910.00` لكل طرف. **يُمنع** تعديل أي صف بالشكل الحديث (الأربعة `draft`) — قيمتها القانونية معبّأة أصلًا ونسخها يضاعفها.
2. **إثبات حفظ المجاميع** قبل/بعد: مجموع المدين والدائن للقيود `posted` ثابت، بلا فقد ولا تكرار. الفشل يُسقط المعاملة.
3. إضافة قيود على الأعمدة **القانونية** `debit`/`credit`: غير سالبة؛ لا يجتمعان بقيمة موجبة؛ لا سطر محاسبي بأصفار كاملة. **بعد** الخطوة 1 حصرًا — إذ إن الأسطر الستة عشر اليوم صفرية القانونية وسترفضها القيود قبل الترحيل.
4. توحيد دقة رأس القيد مع الأسطر بحيث يستوعبان المدى النقدي القانوني نفسه (رفع `numeric(12,2)` في الرأس إلى مدى الأسطر).
5. آلية توافق **مؤقتة** للكتابات الجديدة فقط، بحد إزالة معلن؛ ولا تصبح مصدر حقيقة محاسبية أبدًا.
6. فحوص تكشف — لا تصلح — كل سطر `posted` غير قابل للربط بحساب قانوني، وتُخرجه تقريرًا.
7. **لا ربط حسابات ولا `account_id NOT NULL` تاريخيًا ولا FK** هنا؛ كلها في 154 بعد اعتماد Mapping.

> الأعمدة المولّدة (`GENERATED ALWAYS`) غير مناسبة لاسم/كود الحساب لأنها تحتاج بحثًا عبر الجداول. يجوز trigger انتقالي لتعبئة أعمدة التوافق، بشرط حد إزالة معلن.

#### Migration 154 — الشجرة القانونية والMapping والـFK (بهذا الترتيب)

1. إضافة `UNIQUE (id, org_id)` على `gl_accounts` — **شرط تقني لا يقبل التأجيل**؛ PostgreSQL يرفض FK مركّبًا بلا قيد فريد مطابق.
2. تطبيق سجل Mapping المعتمد على الأسطر التاريخية، وتطبيق قاعدة الحجر على ما قُرِّر حجره.
3. التحقق من **انعدام** Posted Orphans: لا سطر `posted` بلا `account_id` قانوني أو معالجة معتمدة.
4. إنشاء الـFK المركّب:
   ```sql
   gl_entry_lines (account_id, org_id) → gl_accounts (id, org_id)
   ```
5. الانتقال النهائي إلى `account_id`/`debit`/`credit` كمصدر قانوني وحيد في كل قراءة مالية.
6. إبقاء الأعمدة القديمة **انتقالية فقط** مع خطة إزالة وتاريخ في §18.
7. تقرير فروقات يثبت أن **لا قيمة تاريخية فُقدت ولا تكرّرت** (مجاميع posted محفوظة قبل/بعد).

## 5. النطاق

### ضمن النطاق

- قرار Mapping/Quarantine المحاسبي وسجله الموثق.
- توحيد عقد الأعمدة القانونية وقيوده ودقته.
- الشجرة القانونية `gl_accounts` والـFK المركّب مع `UNIQUE (id, org_id)`.
- ميزان مراجعة بافتتاحي وحركة وختامي.
- قائمة دخل مقارنة متعددة المستويات.
- قائمة مركز مالي كما في تاريخ، مع ربح الفترة ضمن حقوق الملكية.
- تدفقات نقدية غير مباشرة ومطابقة النقد.
- كشف حساب وأستاذ عام.
- أساس الأبعاد: الجداول الناقصة، أعمدة الأسطر، تعبئتها في نوى الترحيل، وسياسة NULL التاريخية.
- توحيد عزل الجداول التي يقرؤها المحرك.
- **Onboarding الفترات المحاسبية** وبواباتها.
- Drill-down وExcel/PDF وحفظ العروض.
- RPCs آمنة وقبول Fresh DB **عبر نوى الترحيل الحقيقية**.
- حكم بذور القوالب في الـBaseline.

### خارج النطاق في الإصدار الأول

- Consolidation متعدد الكيانات والعملات، وXBRL، ومحوّلات SQL Server/Oracle.
- موازنات وتوقعات متقدمة قبل صحة التقارير الفعلية.
- مصمم تقارير حر بالكامل.
- **الاستنتاج الآلي للأبعاد التاريخية** حين لم تسجّلها المعاملة المصدرية؛ يُصنَّف التاريخ صراحةً `unknown/unassigned`.
- **الاستنتاج الآلي لـMapping الأكواد التاريخية** (محظور بـADR-FR-014).

## 7. عقد دفتر الأستاذ القانوني

### 7.1 الأعمدة الإلزامية للمصدر

- **النطاق:** `org_id`، معرّفات القيد والسطر، أرقامهما.
- **التاريخ والحالة:** `entry_date` كـ**التاريخ المحاسبي** (`accounting_date`)، و`posted_at` كـ**وقت تدقيق** فقط، و`accounting_periods.id` وحالة الفترة، وحالة القيد. **لا `posting_date`** (ADR-FR-016).
- **الحساب:** `account_id` والكود والاسمان العربي والإنجليزي و`category` و`subtype` و`normal_balance` من `gl_accounts`.
- **المبالغ:** `debit` و`credit` القانونية، والمبلغ الموجَّه، وعملة المعاملة وعملة العرض حيث توفرت.
- **الأبعاد:** مركز التكلفة والربح والقطاع والمشروع والمنتج والشريك — **فقط بعد** اكتمال أعمدتها وبياناتها الأساسية وعزلها.
- **المصدر:** نوع المرجع ومعرّفه ورقمه والوصف ومسار المستند.

### 7.2 القواعد المفروضة في قاعدة البيانات

- حالة الرأس `posted` حصرًا؛ و`draft` و`cancelled` مستبعدان.
- الرأس والسطر والحساب وكل بُعد مُمرَّر في المؤسسة نفسها.
- `account_id` غير فارغ ويشير إلى `gl_accounts` للمؤسسة نفسها عبر FK مركّب.
- `debit` و`credit` القانونية غير سالبتين، ولا تجتمعان بقيمة موجبة، ولا سطر بأصفار كاملة.
- دقة الرأس والأسطر موحّدة؛ لا فائض `numeric(12,2)` في الرأس مقابل `numeric(18,2)` في الأسطر.
- القيد متوازن تحت عقد تقريب ودقة واحد وصريح.
- القيود المعكوسة تتبع عقدًا محاسبيًا واحدًا موثقًا.
- أعمدة الحساب والمبالغ legacy **مستبعدة** من كل حساب مالي جديد.
- `permanently_closed` غير قابلة للترحيل أو إعادة الحساب.

### 7.3 بوابة جاهزية البُعد

قبل أن يعرض المصدر القانوني أي بُعد:

1. جدوله الأساسي موجود ويعزل بـ`org_id`.
2. `gl_entry_lines` يحمل عموده القانوني وفهرسه.
3. كل نواة ترحيل قانونية تعبّئه أو تتركه `unassigned` **بقرار صريح**.
4. سياسة NULL التاريخية موثقة ومعروضة.
5. اختبار عزل يتلاعب بمعرّف ذلك البُعد تحديدًا ويُرفَض.

> View بـ`SECURITY INVOKER` **يجب ألّا** يفقد الأبعاد صامتًا لأن عزلها معلّق على GUC ميت. وRPC بـ`SECURITY DEFINER` **يجب ألّا** يتّكل على تجاوز RLS؛ يقيّد كل جدول مربوط بالمؤسسة في متن الاستعلام.

### 7.4 بوابة الفترات

- Onboarding المؤسسة ينشئ السنة المالية وفتراتها ذريًا (ADR-FR-017).
- المحرك يرفض العمل لمؤسسة بلا فترات بعد تفعيل العلم — **لا يعمل بصمت بلا فترة**.
- `assert_period_open` **fail-open مثبت** عند غياب الفترة؛ لذلك وجود الفترات شرط تشغيلي لا تحسين.

## 8. نموذج بيانات محرك التقارير

| الجدول | الغرض | حالة البيانات المرجعية |
|---|---|---|
| `financial_report_templates` | أنواع التقارير والقوالب النظامية والمخصصة. | صفوف نظامية بـ`org_id IS NULL`؛ **مطلوبة في manifest الـBaseline**. |
| `financial_report_lines` | الشجرة والترتيب والمجاميع. | مطلوبة؛ ترتيب التصدير يحترم `template_id` و`parent_id`. |
| `financial_report_line_rules` | ربط الحسابات والتصنيفات والأبعاد بالأسطر. | مطلوبة؛ بصمة محتوى واختبارات دلالية. |
| `financial_report_formulas` | الأسطر المشتقة كمجمل الربح وصافي الربح. | مطلوبة؛ بعد الأسطر في ترتيب التبعية. |
| `saved_report_views` | فلاتر وأعمدة المستخدم. | org-scoped، ليست بذرة نظامية. |
| `account_period_balances` | تجميع شهري اختياري للأداء. | بيانات تشغيلية تُصان بـjob، ليست بذرة نظامية. |
| `accounting_periods` | الفترات المحاسبية. | **org-scoped من Onboarding** — ليست بذرة نظامية ولا تدخل الـmanifest (ADR-FR-017). |

### 8.1 عقد البذور المرجعية

لا تخرج PR-C حتى تُسجَّل جداول القوالب الأربعة في `sql/baseline/system_reference_manifest.yml` بـ: allowlist صريحة؛ predicate `org_id IS NULL` حيث ينطبق؛ أعمدة متوقعة وترتيب تصدير واعٍ بالتبعية؛ حدود دنيا؛ بصمة محتوى لكل جدول؛ رفض تسرب صفوف org-scoped؛ واختبار دلالي على Fresh DB يُرحّل fixtures **عبر النواة القانونية** ويحصل على **مجمل ربح ≠ صفر** من القالب المبذور.

> **السبب:** وجود الجدول ومساواة `0 = 0` ليسا دليلًا. محرك قوالب فارغ يُخرج قوائم صفرية تعبر كل بوابات المساواة — وهو ما يحدث فعليًا اليوم (§3.2). وقد سبق أن طُويت بذور 130 و140 بالـBaseline فبُنيت كل Fresh DB بجداول UoM فارغة.

### 8.2 عقد التصنيف

تكلفة المبيعات والمصروفات التشغيلية وتقسيم المتداول وأنشطة التدفق **لا** تُصنَّف بـ`LIKE '51%'` ولا بأي اصطلاح كود ضمني. تُدخل PR-C حقل `financial_statement_group` صريحًا أو جدول Mapping مُراجَعًا — وهذا **عمل مخطط جديد**، فالحقل غير موجود اليوم.

### 8.3 الأعمدة المولّدة والمُصانة

- `account_period_balances` الافتتاحي والحركة والختامي أعمدة عادية مُصانة، **لا** `GENERATED ALWAYS`.
- كاتبها idempotent وواعٍ بالفترة ومحجوب عن `permanently_closed`.
- **يُمنع** `SELECT *` ثم spread في أي insert/update في مسارات التقارير — المخطط يحتوي أعمدة مولّدة (22 وقت Baseline 121، وأضاف 149 عمودًا آخر).
- الأعمدة المولّدة تُختار صراحةً كمخرجات قراءة فقط.

## 9. عقد الاستعلام الموحد

```sql
rpc_get_financial_report(
  p_report_code       text,
  p_from_date         date,
  p_to_date           date,
  p_comparison_from   date    default null,
  p_comparison_to     date    default null,
  p_filters           jsonb   default '{}'::jsonb,
  p_include_zero      boolean default false,
  p_detail_level      integer default 2
)
```

- `SECURITY DEFINER` عند الحاجة مع `SET search_path = public, pg_temp`، وسحب EXECUTE من PUBLIC وanon، ومنح الأدوار اللازمة فقط.
- اشتقاق المؤسسة من الجلسة والتحقق من العضوية داخل الدالة.
- الفلترة الزمنية على **`entry_date`** (التاريخ المحاسبي)، لا على `posted_at` (ADR-FR-016).
- استخدام `accounting_periods` صراحةً والتحقق من الحالات الثلاث؛ القراءة مسموحة لكل الفترات الصحيحة، والترحيل/إعادة الإفصاح في `permanently_closed` ممنوع.
- **رفض العمل لمؤسسة بلا فترات** بعد تفعيل العلم، بخطأ صريح لا نتيجة صامتة.
- بنية صفوف موحدة للحالية والمقارنة والانحراف، وmetadata للعملة والوحدة وتاريخ آخر قيد وحالة الفترة وأعلام الجودة.
- رفض معرّفات الحسابات **والأبعاد** من مؤسسة أخرى ولو مُرِّرت في `p_filters`.
- `label_ar` و`label_en` من بيانات القوالب، لا من مكوّن React.
- عقود التفصيل تستخدم **نفس** المصدر والفلاتر التي استخدمها سطر الملخص.

| الحقل | الوصف |
|---|---|
| `line_key` / `parent_key` / `level` | هوية السطر وشجرته. |
| `label_ar` / `label_en` | اسم العرض ثنائي اللغة من البيانات. |
| `line_type` | `account` أو `subtotal` أو `formula` أو `heading`. |
| `current_amount` / `comparison_amount` | قيمة الفترة الحالية وفترة المقارنة. |
| `variance_amount` / `variance_percent` | الانحراف قيمةً ونسبةً. |
| `drilldown_key` | مفتاح آمن لجلب الحسابات والقيود الداعمة. |
| `quality_flags` | عدم مطابقة، فترة مفتوحة، **سطور بلا حساب قانوني**، **مؤسسة بلا فترات**، بيانات غير مصنفة. |

## 10. متطلبات القوائم

### ميزان المراجعة
افتتاحي وحركة وختامي بالمدين والدائن؛ تواريخ بداية ونهاية حقيقية؛ حسابات صفرية اختيارية وتجميع بالمستويات؛ إجمالي المدين = إجمالي الدائن في الثلاثة؛ والنقر على الحساب يفتح كشف الحساب بالفترة نفسها.

### قائمة الدخل
| # | السطر | النوع |
|---|---|---|
| 1 | المبيعات الإجمالية | تفصيلي |
| 2 | مردودات وخصومات المبيعات | تفصيلي |
| 3 | صافي المبيعات | صيغة |
| 4 | تكلفة المبيعات | تفصيلي |
| 5 | مجمل الربح | صيغة |
| 6 | مصروفات البيع والتوزيع | مجموعة |
| 7 | المصروفات الإدارية والعمومية | مجموعة |
| 8 | الربح التشغيلي | صيغة |
| 9 | تكاليف التمويل والإيرادات/المصروفات الأخرى | مجموعة |
| 10 | الربح قبل الزكاة والضريبة ثم صافي الربح | صيغة |

### قائمة المركز المالي
أصول متداولة ثم غير متداولة؛ خصوم متداولة ثم غير متداولة؛ حقوق الملكية (رأس المال والاحتياطيات والأرباح المبقاة وربح الفترة)؛ تحقق آلي من `الأصول = الخصوم + حقوق الملكية` **مع إثبات أن الطرفين غير صفريين** عند وجود حركة؛ وعدم الإقفال لا يُنتج ميزانية غير متوازنة.

### التدفقات النقدية — غير مباشرة
تشغيلية واستثمارية وتمويلية؛ نقد أول الفترة + صافي التغير = نقد آخر الفترة؛ والختامي يطابق حسابات النقد والبنوك في المركز المالي.

### كشف الحساب والأستاذ العام
رصيد افتتاحي مستقل قبل بداية الفترة؛ ترتيب حتمي بالتاريخ ورقم القيد ورقم السطر؛ رصيد جارٍ يحترم `normal_balance`؛ عرض المرجع والوصف والأبعاد والمستند؛ **ولا fallback يبدأ من صفر** — فشل RPC يظهر خطأً صريحًا.

## 11. الواجهة والتصدير

**شريط الفلاتر:** الفترة والنطاقات السريعة؛ المقارنة أو الموازنة؛ مركز التكلفة والربح والقطاع والمشروع والمنتج والشريك والفرع؛ مستوى التفصيل وإخفاء الصفر ووحدة العرض وإظهار الأكواد؛ تشغيل وتحديث وExcel وPDF وطباعة وحفظ العرض.

**الجدول:** توسيع وطي مع الحفاظ على ترتيب القالب؛ تثبيت عمود البيان والإجماليات؛ الحالية والمقارنة والانحراف؛ السالب بين أقواس؛ إظهار العملة والوحدة ووقت الاستخراج وحالة الفترة؛ **تنبيه مرئي عند سطور بلا حساب قانوني أو قيود مسودة أو مؤسسة بلا فترات**؛ Drill-down من السطر إلى الحساب إلى القيد إلى المستند؛ ودعم RTL/LTR والطباعة المتجاوبة.

**قاعدة i18n ملزمة:** تسميات أسطر التقارير تأتي من `label_ar`/`label_en` التي يعيدها المحرك. أي تعبير في PR-D يكافئ `isRTL ? 'نص عربي' : 'English text'` لتسمية سطر تقرير **مخالفة تحجبها بوابة CI**. عناصر التطبيق الثابتة تبقى على مفاتيح الترجمة.

**PDF وExcel:** هوية المنشأة والشعار والرقم الضريبي واسم التقرير والفترة والعملة ووقت الاستخراج؛ تكرار رؤوس الأعمدة وترقيم الصفحات؛ عدم قص الأسماء العربية ولا عكس الأعمدة في RTL؛ أرقام حقيقية وتنسيقات مناسبة في Excel؛ وتطابق الإجماليات حرفيًا مع الشاشة والـAPI.

## 12. الأداء

تجميع على الخادم؛ فهارس على المؤسسة والحالة والتاريخ والقيد والحساب؛ keyset pagination للتفاصيل؛ `account_period_balances` عند الحاجة؛ و`EXPLAIN ANALYZE` على بيانات تمثيلية قبل الاعتماد.

الأهداف الأولية: القائمة الأساسية حتى 500 حساب تحت ثانيتين في بيئة إنتاج معتادة؛ أول صفحة Drill-down تحت ثانيتين ونصف؛ ولا نقل لكل سطور GL إلى المتصفح.

> **قياس مرجعي مطلوب:** الأرقام أعلاه أهداف لا خطوط أساس. تُقاس فعليًا في PR-B على بيانات حجمية قبل الالتزام النهائي بها.

## 13. الأمن والعزل متعدد المؤسسات

- RLS على جداول القوالب والقواعد والعروض المحفوظة.
- سحب EXECUTE من PUBLIC وanon إلا للواجهات المقصودة؛ وhelpers الداخلية لا تُمنح لـ`anon` أو`authenticated`.
- المؤسسة والعضوية تُشتقان وتُتحققان داخل RPC؛ ولا `org_id`/`tenant_id` مقبول من الواجهة بلا تحقق.
- فلاتر الأبعاد لا تقبل معرّفات مؤسسة أخرى، والفشل حقيقي حتى مع تلاعب الشبكة.
- استبدال كل سياسة `app.current_tenant_id` **في الجداول التي يقرؤها المحرك** بحارس `org_id` النشط قبل إدخال ربط الأبعاد.
- اختبارات الأمن تغطي **معرّف بُعد واحدًا على الأقل** إضافة إلى الحساب والقيد.
- دوال `SECURITY DEFINER` تقيّد كل جدول مربوط بالمؤسسة في متنها؛ ونجاح عزل الدفتر **ليس** دليلًا على عزل الأبعاد.
- **اختبار العزل ينشئ Organization A وOrganization B داخل Fresh DB fixtures.** لا يُعتمد على Production الحالية — فيها **مؤسسة واحدة فقط** (§3.1)، فالبوابة غير قابلة للتنفيذ عليها ولا تُعدّ ممرَّرة بها.
- أعلام الميزات org-scoped في `org_settings`؛ ومفتاح محرك التقارير: `financial_reporting_engine_v2_enabled`.

```sql
SELECT org_id, value
FROM public.org_settings
WHERE key = 'financial_reporting_engine_v2_enabled';
```

## 14. الاختبارات ومعايير القبول

### 14.1 بوابات FIN-REP-000

- [ ] **الـfixtures تُنشأ عبر نواة الترحيل القانونية** (`rpc_create_journal_entry` أو ما يستدعيها)، **لا** بـ`INSERT` مباشر في `gl_entry_lines`.
- [ ] **قيود `draft` و`cancelled` لا تدخل أي تقرير مالي.** الأسطر الأربعة الحديثة الحالية مسودات، فبقاؤها مستبعدة **هو** السلوك الصحيح ولا يُطلب ظهورها.
- [ ] **قيد جديد يُرحَّل بالشكل الحديث عبر النواة القانونية يظهر في ميزان المراجعة والقوائم وكشف الحساب بمبلغه الدقيق** — هذا هو إثبات إغلاق F-10.
- [ ] **مجموع المدين والدائن لكل القيود `posted` محفوظ قبل وبعد توحيد العقد، بلا فقد ولا تكرار** (ثابت محفوظ، لا مبلغ مثبَّت في النص).
- [ ] **بعد ترحيل المبالغ، تحمل الأعمدة القانونية كامل مجموع القيود `posted`** الذي كان في الأعمدة legacy — ولا يبقى سطر `posted` بمبلغ قانوني صفري ومبلغ legacy موجب.
- [ ] **لم يتضاعف أي مبلغ:** الأسطر التي كانت بالشكل الحديث أصلًا لم تُنسخ إليها قيمة legacy.
- [ ] **لا يبقى أي سطر `posted` بلا `account_id` قانوني أو معالجة معتمدة** (Mapping أو Quarantine).
- [ ] تفشل البوابة عند أي **كود تاريخي مجهول** أو **Mapping ملتبس** — ولا تُستنتج المعالجة آليًا.
- [ ] `UNIQUE (id, org_id)` قائم على `gl_accounts` قبل إنشاء الـFK المركّب.
- [ ] قيود المبالغ القانونية ترفض السالب والموجب المزدوج والسطر الصفري بالكامل.
- [ ] دقة الرأس والأسطر تستوعبان المدى النقدي القانوني نفسه، مع اختبارات حدّية قرب الحد الأقصى.
- [ ] تتطابق نتائج ميزان المراجعة والقوائم وكشف الحساب **للقيود نفسها**.

### 14.2 البوابات المحاسبية الأساسية

- [ ] `draft` لا يؤثر في أي تقرير.
- [ ] `cancelled` لا يؤثر في أي تقرير.
- [ ] `posted` يؤثر في ميزان المراجعة والأستاذ والقوائم **بالقيمة نفسها**.
- [ ] افتتاحي + حركة = ختامي لكل حساب.
- [ ] إجمالي المدين = إجمالي الدائن في ميزان المراجعة.
- [ ] `الأصول = الخصوم + حقوق الملكية`، **والطرفان غير صفريين عند وجود حركة**.
- [ ] ربح الفترة يظهر في حقوق الملكية قبل الإقفال.
- [ ] صافي ربح قائمة الدخل يطابق حسابات الإيراد والمصروف في الأستاذ.
- [ ] كشف الحساب يطابق ميزان المراجعة للحساب والتاريخ نفسيهما.
- [ ] النقد الختامي في التدفقات يطابق النقد والبنوك في المركز المالي.
- [ ] القيود المعكوسة تغيّر كل التقارير باتساق.

### 14.3 بوابات الفترات

- [ ] Fresh DB ينشئ فترات fixture للسنة المالية.
- [ ] الترحيل إلى فترة `closed` **مرفوض**.
- [ ] أي تعديل أو قيد رجعي إلى `permanently_closed` **مرفوض**.
- [ ] القراءة من الفترات المقفلة **مسموحة**.
- [ ] المحرك **يرفض** العمل لمؤسسة بلا فترات بعد تفعيل العلم، أو يوفّر Onboarding ذريًا ينشئ السنة والفترات.
- [ ] اختبار يثبت أن غياب الفترات **لا** يمرّ بصمت كما يفعل `assert_period_open` اليوم (F-14).

### 14.4 بوابات الأمن والأبعاد والتفصيل

- [ ] طلبات الحسابات عبر المؤسسات مرفوضة.
- [ ] طلبات **الأبعاد** عبر المؤسسات مرفوضة لمركز التكلفة أو القطاع على الأقل.
- [ ] الاختبار **ينشئ مؤسستين في Fresh DB** ولا يعتمد على Production.
- [ ] لا بُعد يصبح NULL صامتًا بسبب RLS الميت.
- [ ] كل صف يتوسع إلى القيود والمستندات الداعمة بدقة.

### 14.5 بوابات البيانات المرجعية وFresh DB

- [ ] Fresh DB يطبّق كل migrations وطبقتَي الـBaseline المقترنتين.
- [ ] جداول القوالب تحقق الحدود الدنيا والبصمات من `system_reference_manifest.yml`.
- [ ] لا تسرب لصفوف org-scoped في اللقطة النظامية.
- [ ] fixture مُرحَّل عبر النواة القانونية يُخرج **صافي مبيعات وتكلفة مبيعات ومجمل ربح ≠ صفر** من القالب المبذور.
- [ ] بذرة قوالب فارغة أو ناقصة **تُفشل CI**، ولا تُنتج قائمة صفرية «ناجحة».

### 14.6 بوابات الواجهة والتصدير

- [ ] إجماليات Excel/PDF = إجماليات الـAPI = إجماليات الشاشة.
- [ ] تسميات الأسطر من بيانات ثنائية اللغة لا من نصوص المكوّن.
- [ ] العلم مطفأ ⇒ مسار legacy معتمد أو حجب ظاهر؛ **ولا تبديل صامت** بين تعريفين محاسبيين.

### 15.3 فصل النشر الإلزامي

PR قاعدة البيانات وPR التطبيق/الواجهة التابع له **لا يُدمجان كوحدة نشر واحدة**:

1. دمج PR الـmigration إلى `main` (**repository-first**؛ لا تطبيق SQL غير موجودة في `main` بأي حال).
2. تطبيق الـmigrations على Production بالترتيب الدقيق.
3. التحقق من السجل والقيود ومطابقة البيانات والصلاحيات وحالة العلم.
4. تفعيل العلم لمؤسسة واحدة مضبوطة.
5. دمج/نشر PR التطبيق التابع (**DB-first**).
6. توسيع الإطلاق بعد القبول المحاسبي.

**قاعدة الدمج:** لا واجهة تقارير جديدة قبل مرور حزم الدقة والمصدر القانوني والبذور. ولا يُحذف مسار قديم إلا بعد مقارنة مزدوجة مؤقتة تثبت التطابق أو تفسّر الفروقات بسببها (`draft`، `journal_legacy`، تصنيف، فترة، إشارة، **كود غير مربوط**).

## ملحق C — استعلامات التحقق الإلزامية

على PR التنفيذ أن يضم سكربتات مُصانة تجيب على الأقل عن:

```sql
-- 1) عقد الأعمدة المزدوج قبل/بعد، مع حالة القيد (لا خلط draft بـposted)
SELECT e.status,
       count(*)                                                    AS lines,
       count(*) FILTER (WHERE l.account_id IS NOT NULL
                          AND l.account_code IS NULL)              AS modern_only,
       sum(l.debit)        AS canon_debit,  sum(l.credit)        AS canon_credit,
       sum(l.debit_amount) AS legacy_debit, sum(l.credit_amount) AS legacy_credit
FROM public.gl_entry_lines l
JOIN public.gl_entries e ON e.id = l.entry_id
GROUP BY e.status ORDER BY e.status;

-- 2) الأكواد التاريخية غير القابلة للحل (يجب أن يصبح صفرًا بعد 154)
SELECT l.org_id, l.account_code, count(*) AS lines
FROM public.gl_entry_lines l
JOIN public.gl_entries e ON e.id = l.entry_id
WHERE e.status = 'posted'
  AND l.account_code IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM public.gl_accounts a
                  WHERE a.org_id = l.org_id AND a.code = l.account_code)
GROUP BY l.org_id, l.account_code ORDER BY l.account_code;

-- 3) Posted orphans: سطر مرحّل بلا حساب قانوني (يجب أن يكون صفرًا)
SELECT count(*) AS posted_orphans
FROM public.gl_entry_lines l
JOIN public.gl_entries e ON e.id = l.entry_id
LEFT JOIN public.gl_accounts a ON a.id = l.account_id AND a.org_id = l.org_id
WHERE e.status = 'posted' AND a.id IS NULL;

-- 4) شرط الـFK المركّب (يجب أن يعيد صفًا قبل إنشاء الـFK)
SELECT conname, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'public.gl_accounts'::regclass
  AND contype = 'u'
  AND pg_get_constraintdef(oid) ILIKE '%(id, org_id)%';

-- 5) سياسات المؤسسة الميتة المتبقية
SELECT tablename, policyname
FROM pg_policies
WHERE schemaname = 'public'
  AND (coalesce(qual, '')       ILIKE '%app.current_tenant_id%'
    OR coalesce(with_check, '') ILIKE '%app.current_tenant_id%')
ORDER BY tablename;

-- 6) تغطية الفترات: مؤسسة بلا فترات، وقيود بلا فترة مطابقة
SELECT o.id AS org_id,
       (SELECT count(*) FROM public.accounting_periods p WHERE p.org_id = o.id) AS periods,
       (SELECT count(*) FROM public.gl_entries e
        WHERE e.org_id = o.id
          AND NOT EXISTS (SELECT 1 FROM public.accounting_periods p
                          WHERE p.org_id = e.org_id
                            AND e.entry_date BETWEEN p.start_date AND p.end_date)
       ) AS entries_without_period
FROM public.organizations o ORDER BY o.id;

-- 7) علم الإطلاق
SELECT org_id, value
FROM public.org_settings
WHERE key = 'financial_reporting_engine_v2_enabled';
```
