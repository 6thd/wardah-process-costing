# برنامج وردة ERP — عقد محرك التقارير والقوائم المالية

**المعرف:** `WRD-FIN-REP-SRS-001`  
**الإصدار:** `1.3`  
**التاريخ:** 30 يوليو 2026  
**الحالة:** جاهزة للمراجعة والاعتماد عبر PR؛ لا تُعد معتمدة قبل الدمج.  
**خط الأساس البرمجي:** `main @ 1ef28f396b2cb73bc3c5e75e7054f87eadda7bd4`  
**خط أساس قاعدة البيانات:** Production وRepository وBaseline عند cutoff **152**. أول رقم محجوز: **153**.

## 1. غرض الوثيقة

تعريف عقد تنفيذي قابل للاختبار لبناء محرك تقارير مالية موحد وآمن ومتعدد المؤسسات فوق:

- `gl_entries` و`gl_entry_lines` بوصفهما دفتر الأستاذ القانوني.
- `gl_accounts` بوصفها شجرة الحسابات القانونية.
- `account_id` و`debit` و`credit` بوصفها الأعمدة القانونية.
- قيود `posted` فقط بوصفها المؤثرة في التقارير.

لا تنفذ هذه الوثيقة Migration، ولا تغيّر Production، ولا تعتمد Mapping تاريخيًا بالتخمين.

## 2. النتائج المثبتة التي تحكم التصميم

1. خدمة القوائم الحالية تقرأ أسطر GL بلا ربط قانوني كافٍ برأس القيد وبلا عقد posted-only موحد.
2. توجد مسارات تقريرية متباينة بين `gl_*` و`journal_*` وfallbacks في التطبيق.
3. النواة القانونية تكتب `account_id + debit/credit` بينما بعض القراءات والـfixtures تعتمد `account_code + debit_amount/credit_amount`.
4. الأسطر الحديثة الأربعة الحالية `draft`، ولذلك استبعادها صحيح محاسبيًا.
5. الأسطر الستة عشر `posted` تحمل المال في الأعمدة legacy وأكوادًا رباعية لا تنتمي إلى شجرة الحسابات السداسية الحالية.
6. ترحيل **المبالغ** من legacy إلى القانونية ميكانيكي وحتمي؛ أما ربط **الحسابات** فهو قرار محاسبي غير قابل للاستنتاج.
7. `gl_entry_lines.account_id` بلا FK إلى `gl_accounts` داخل المؤسسة نفسها، و`gl_accounts` لا تحمل بعد `UNIQUE (id, org_id)`.
8. `accounting_periods` بلا صفوف في الحالة الحية الموثقة، و`assert_period_open` تمر عند غياب فترة؛ لذا Onboarding الفترات وبوابة fail-closed لازمان قبل تشغيل المحرك.
9. الأبعاد غير جاهزة كمصدر قانوني كامل، وبعض جداولها تعتمد GUC ميتًا.

## 3. القرارات المعمارية الملزمة

### ADR-FR-001 — المصدر القانوني

كل تقرير مالي جديد يقرأ من `gl_entries` و`gl_entry_lines` فقط. `journal_entries` و`journal_lines` تاريخيان ولا ينشأ عليهما مسار جديد.

### ADR-FR-002 — الحالة المحاسبية

`posted` فقط تؤثر في التقارير. `draft` و`cancelled` مستبعدتان باختبارات صريحة.

### ADR-FR-003 — المؤسسة

المؤسسة تُشتق من الجلسة ويُتحقق من العضوية داخل RPC. لا UUID ثابت ولا ثقة في `org_id` قادم من المتصفح.

### ADR-FR-004 — الحساب والمبلغ القانونيان

- الشجرة القانونية: `gl_accounts`.
- الهوية القانونية: `account_id`.
- المبالغ القانونية: `debit` و`credit`.
- أعمدة `account_code`, `account_name`, `debit_amount`, `credit_amount` توافق انتقالية فقط، ولا تدخل أي حساب مالي جديد.

### ADR-FR-005 — التاريخ والفترات

- `entry_date` هو التاريخ المحاسبي.
- `posted_at` وقت تدقيق فقط.
- لا يُضاف `posting_date` دون ADR مستقل.
- المحرك يرفض العمل لمؤسسة بلا فترات بعد تفعيل العلم.
- `permanently_closed` للقراءة فقط، ولا تعديل أو ترحيل رجعي دون إجراء إعادة إفصاح مستقل.

### ADR-FR-006 — Mapping التاريخي

ربط كل كود تاريخي بحساب قانوني قرار محاسبي معتمد لكل كود على حدة. يمنع الربط بالتشابه أو البادئة أو طول الكود.

### ADR-FR-007 — الحجر Quarantine

الحجر ليس حذفًا ولا تعديلًا صامتًا. أي سطر تاريخي غير قانوني يُعالج بإحدى طريقتين معتمدتين:

1. **عكس/إعادة تصنيف قانوني:** يبقى الأصل كما هو، ويُنشأ قيد مقابل أو إعادة تصنيف مرتبطة به.
2. **استبعاد تدقيقي صريح:** يُسجل في جدول حجر قانوني، ويُستبعد من المصدر التقريري مع بقاء السطر الأصلي دون تغيير.

لا يجوز استخدام علم عام غير موثق أو شرط مخفي في View.

## 4. عقد الحجر القابل للفرض

ينشأ في Migration 154 عند اختيار مسار الاستبعاد جدول مثل:

```sql
financial_gl_quarantine (
  id uuid primary key,
  org_id uuid not null,
  gl_entry_line_id uuid not null,
  treatment text not null check (treatment in ('exclude','reversal','reclassification')),
  reason_code text not null,
  reason_detail text not null,
  accounting_effect text not null,
  approved_by uuid not null,
  approved_at timestamptz not null,
  decision_reference text not null,
  reversal_entry_id uuid null,
  created_at timestamptz not null default now(),
  unique (org_id, gl_entry_line_id)
)
```

القواعد الملزمة:

- كل صف حجر مرتبط بسطر GL في المؤسسة نفسها عبر FK مركب أو تحقق قانوني مكافئ.
- `exclude` يعني أن السطر غير **reportable**، لكنه يبقى مرئيًا في تقارير الجودة والتدقيق.
- `reversal` و`reclassification` لا يصبحان نافذين إلا عند وجود قيد مقابل `posted` مرتبط.
- لا سطر `posted` يدخل المصدر القانوني النهائي بلا `account_id` صالح، إلا إذا كان له سجل حجر معتمد قابل للتدقيق.
- المصدر القانوني يعيد `quality_flags` وعدد/قيمة الأسطر المحجورة، ولا يخفيها عن المراجع.
- **أمن الجدول جزء من Migration 154 نفسها ولا يؤجل إلى 155:** فور الإنشاء وقبل إدخال أي قرار، تُسحب صلاحيات الجدول من `PUBLIC` و`anon` و`authenticated`، وتُفعّل `ENABLE ROW LEVEL SECURITY` و`FORCE ROW LEVEL SECURITY`، وتُنشأ سياسات القراءة/الإدارة المقصودة أو تُحصر القراءة والكتابة في RPCs محروسة.
- لا كتابة مباشرة من العميل إلى جدول الحجر. الإدخال أو التعديل يتم عبر migration معتمدة أو واجهة إدارية ذرية تتحقق من المؤسسة والصلاحية والاعتماد المحاسبي.
- يجب أن يثبت Fresh DB أن `anon` وعضوًا غير مخول لا يستطيعان قراءة أو إنشاء أو تعديل أو حذف قرار حجر، وأن معرّف مؤسسة أخرى مرفوض.

تعريف الاكتمال الأدق:

> لا سطر **reportable posted** بلا `account_id` قانوني. والأسطر المحجورة مستبعدة بعقد قاعدة بيانات معلن، مع سبب ومعتمد وتاريخ وأثر محاسبي.

## 6. Migration 153 — عقد مستقل للمبالغ والقيود والدقة

### 6.1 النطاق

- نسخ المبالغ legacy إلى `debit/credit` داخل الصف نفسه.
- إضافة قيود قانونية على `debit/credit`.
- توحيد دقة رأس القيد والأسطر.
- توافق مؤقت للكتابات الجديدة.
- كشف الأسطر غير القابلة للربط دون إصلاح حساباتها.

ممنوع في 153:

- Mapping حسابات.
- تعبئة `account_id` تاريخيًا.
- `account_id NOT NULL`.
- FK إلى `gl_accounts`.
- أي قرار حجر.

### 6.2 القفل والتزامن

قبل snapshot أو backfill، تُكتسب الأقفال بترتيب الكتابة الطبيعي **الرأس أولًا ثم السطور**، ويفضل في statement واحدة:

```sql
LOCK TABLE public.gl_entries,
           public.gl_entry_lines
IN SHARE ROW EXCLUSIVE MODE;
```

يُمنع ترتيب child-first لأنه قد يتعارض مع جلسة أنشأت رأس القيد ثم تنتظر إدخال السطور. يجوز اختيار قفل أشد إن أثبتت المراجعة الحاجة، لكن يمنع تنفيذ backfill مع كتابات متزامنة تغير مجموعة الصفوف أو مجاميعها.

اختبار التزامن الإلزامي يشغّل كاتبًا بالنمط القانوني `gl_entries → gl_entry_lines` بالتوازي مع 153، ويثبت عدم وقوع deadlock وأن أحد المسارين ينتظر بصورة حتمية ثم يكتمل دون drift أو فقد.

### 6.3 Preflight إلزامي

تُحسب الأعداد والمجاميع وقت التنفيذ، ولا تُثبت قيمة `16` أو `19,910` في شرط نجاح Production.

يفشل التنفيذ عند وجود أي صف:

- `debit < 0` أو `credit < 0` أو legacy سالب.
- كل من المدين والدائن موجب.
- مبلغ قانوني موجب ومبلغ legacy موجب في الاتجاه نفسه بصورة متعارضة.
- `account_id` و`account_code` معبآن معًا في شكل ملتبس غير موثق.
- صف لا ينتمي بوضوح إلى modern-only أو legacy-only أو empty legal row مقبول.

يُحفظ snapshot داخل المعاملة يتضمن:

- عدد الصفوف حسب حالة الرأس وشكل السطر.
- مجموع `posted` للمدين والدائن القانوني والـlegacy.
- عدد الصفوف المستهدفة للنسخ.
- بصمة أو قائمة IDs للصفوف المستهدفة عند الحجم الحالي المعقول.

### 6.4 نافذة الصيانة لحماية الأسطر المرحّلة

الأسطر المستهدفة `posted` وتحميها `trg_protect_posted_gl_entry_lines` من أي `UPDATE`. لذلك لا يجوز أن يفترض backfill إمكان تحديثها مباشرة، ولا يجوز إنشاء bypass دائم أو GUC يستطيع التطبيق استعمالها.

بعد اكتساب الأقفال وإتمام preflight، تستخدم Migration 153 نافذة صيانة **داخل المعاملة نفسها**:

1. التحقق من وجود trigger الحماية واسمه وحالته المتوقعة؛ الغياب أو التعطيل المسبق يفشل migration.
2. تعطيل **الـtrigger المسمى فقط** على `gl_entry_lines`، لا `DISABLE TRIGGER USER` ولا `session_replication_role`.
3. تنفيذ backfill على مجموعة IDs المحسوبة وحدها، مع `UPDATE ... RETURNING`.
4. إعادة تفعيل trigger الحماية قبل أي COMMIT.
5. التحقق من `pg_trigger.tgenabled` ومن أن محاولة تعديل سطر `posted` بعد إعادة التفعيل تعيد `POSTED_ENTRY_IMMUTABLE`.

الأقفال تمنع أي كاتب آخر من استغلال نافذة التعطيل. وأي فشل قبل COMMIT يسقط المعاملة كلها، بما فيها DDL المؤقت، لكن التحقق الصريح من إعادة التفعيل يظل بوابة إلزامية.

### 6.5 شرط النسخ

```sql
WHERE account_id IS NULL
  AND debit = 0
  AND credit = 0
  AND (debit_amount > 0 OR credit_amount > 0)
```

ينفذ `UPDATE ... RETURNING id`، ويجب أن يساوي عدد الصفوف المعادة العدد المحسوب في preflight، وأن تطابق IDs المعادة مجموعة الهدف المحفوظة. أي فرق يسقط المعاملة.

### 6.6 فحوص ما بعد النسخ

داخل المعاملة وقبل COMMIT:

- مجاميع `posted` الاقتصادية محفوظة بلا فقد أو تضاعف.
- لا صف مستهدف بقي قانونيًا صفريًا مع legacy موجب.
- الصفوف الحديثة السابقة لم تتغير.
- كل صف قانوني: غير سالب، لا موجب مزدوج، ولا صفر كامل لصف محاسبي فعلي.
- اتزان كل قيد `posted` محفوظ.
- trigger حماية posted عاد مفعّلًا ويمنع التعديل العام.

### 6.7 التوافق المؤقت واتجاهه

الاتجاه القانوني الوحيد للكتابات الجديدة:

```text
account_id + debit/credit  →  أعمدة legacy للقراءة القديمة عند الحاجة
```

يمنع الاتجاه العكسي للكتابات الجديدة؛ legacy لا تصبح مصدر حقيقة مرة أخرى.

آلية التوافق يجب أن تكون محدودة ومعلنة، مثل trigger يملأ الكود/الاسم والمبالغ legacy من القيم القانونية، مع:

- منع التعارض إن أرسل الكاتب شكلين مختلفين.
- عدم تعديل الأسطر `posted` التاريخية بعد backfill.
- اختبارات على النواة القانونية الحقيقية.

### 6.8 شرط إزالة التوافق

تزال آلية التوافق فقط بعد تحقق جميع الآتي:

1. كل مستهلك مالي في التطبيق وRPCs يقرأ الأعمدة القانونية.
2. لا كتابة إنتاجية تعتمد أعمدة legacy لمدة إصدارين متتاليين أو نافذة تشغيل معتمدة.
3. مقارنة مزدوجة تثبت التطابق.
4. Migration إزالة مستقلة مع runbook وrollback منطقي.

## 7. Migration 154 — الحسابات وMapping والحجر والـFK

تبدأ فقط بعد اعتماد سجل القرار المحاسبي.

الترتيب الملزم:

1. إنشاء `UNIQUE (id, org_id)` على `gl_accounts`.
2. إنشاء عقد الحجر إن اختير الاستبعاد، ثم **في التغيير نفسه وقبل أي INSERT**:
   - `REVOKE ALL` من `PUBLIC`, `anon`, `authenticated`.
   - `ENABLE ROW LEVEL SECURITY` و`FORCE ROW LEVEL SECURITY`.
   - إنشاء سياسات/RPCs org-safe المقصودة واختبارات grants السلبية.
3. تطبيق Mapping المعتمد فقط.
4. تطبيق قرارات الحجر المعتمدة فقط عبر المسار المحروس.
5. فحص عدم وجود سطر `reportable posted` بلا حساب قانوني.
6. إنشاء FK المركب:

```sql
gl_entry_lines (account_id, org_id)
  → gl_accounts (id, org_id)
```

7. تقرير فروقات يثبت حفظ القيم التاريخية وعدم مضاعفتها.

لا يجوز الاعتماد على Migration 155 لتأمين `financial_gl_quarantine`؛ نافذة غير محمية بين 154 و155 مخالفة حاجزة.

## 10. عقد المصدر والاستعلام

المصدر القانوني النهائي:

- يربط الرأس والسطر والحساب داخل المؤسسة نفسها.
- يرشح `posted` فقط.
- يستبعد `exclude` المحجور ويعرضه في quality metadata.
- يستخدم `entry_date` للفترة.
- لا يعتمد أعمدة legacy.
- لا يفقد بُعدًا صامتًا بسبب RLS.

RPC المستهدفة:

```sql
rpc_get_financial_report(
  p_report_code text,
  p_from_date date,
  p_to_date date,
  p_comparison_from date default null,
  p_comparison_to date default null,
  p_filters jsonb default '{}'::jsonb,
  p_include_zero boolean default false,
  p_detail_level integer default 2
)
```

متطلبات الأمن:

- `SET search_path = public, pg_temp` عند `SECURITY DEFINER`.
- سحب EXECUTE من PUBLIC وanon.
- التحقق من العضوية والمؤسسة داخل الدالة.
- رفض account/dimension IDs من مؤسسة أخرى.
- إنشاء مؤسستين في Fresh DB لاختبارات العزل.

## 12. بوابات القبول الأساسية

### 12.1 Migration 153

- Fresh DB من Baseline cutoff 152.
- القفل parent-first قبل snapshot/backfill.
- اختبار الكاتب القانوني المتزامن يثبت عدم deadlock وعدم drift.
- preflight يفشل عند mixed أو ambiguous rows.
- trigger حماية posted موجود ومفعّل قبل نافذة الصيانة.
- تعطيل trigger المسمى فقط تحت الأقفال؛ لا bypass دائم ولا `session_replication_role`.
- عدد `UPDATE ... RETURNING` وIDs المعادة يطابقان الهدف الديناميكي.
- مجاميع posted محفوظة.
- لا تضاعف للصفوف الحديثة.
- قيود السالب والموجب المزدوج والصفر الكامل تعمل.
- trigger حماية posted مفعّل قبل COMMIT، واختبار `POSTED_ENTRY_IMMUTABLE` يمر بعد backfill.
- التوافق اتجاهه legal → legacy فقط ويمنع التعارض.

### 12.2 Migration 154

- كل كود له قرار معتمد.
- لا Mapping مستنتج آليًا.
- لا `reportable posted orphan`.
- الحجر يحمل السبب والمعتمد والتاريخ والأثر.
- أمن جدول الحجر يُفرض داخل 154 قبل إدخال الصفوف: grants مسحوبة، RLS وFORCE مفعّلان، واختبارات anon/cross-org سلبية.
- لا كتابة مباشرة من العميل إلى قرارات الحجر.
- `UNIQUE (id, org_id)` يسبق FK.
- FK cross-org يرفض.

### 12.3 التقارير

- `draft` و`cancelled` مستبعدتان.
- قيد حديث `posted` يظهر بالقيمة نفسها في Trial Balance وGL والقوائم.
- افتتاحي + حركة = ختامي.
- إجمالي المدين = إجمالي الدائن.
- الأصول = الخصوم + حقوق الملكية، والطرفان غير صفريين عند وجود حركة.
- كشف الحساب يطابق ميزان المراجعة.
- Excel/PDF/API/UI متطابقة.
- المحرك يرفض مؤسسة بلا فترات بعد تفعيل العلم.

## 13. ترتيب النشر

لكل Migration:

1. فرع من أحدث `main`.
2. PR قاعدة بيانات مستقل.
3. CI وFresh DB وMigration Governance ومراجعة أمنية.
4. دمج إلى `main`.
5. تطبيق على Production بالاسم القانوني نفسه.
6. فحوص قبل/بعد وسجل migration مرة واحدة.
7. ثم فقط دمج التطبيق/الواجهة التابعة.
8. تحديث Baseline بعد ظهور Migration في سجل Production عبر workflow وPR مستقل.

لا SQL على Production قبل وجودها في `main`، ولا واجهة تعتمد Schema غير مطبقة.
