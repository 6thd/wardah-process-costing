# خطة مواءمة المستودع والواجهة مع الصورة الحقيقية للمنتج

**التاريخ:** 2026-08-26  
**النوع:** قراءة وتحليل وتخطيط فقط — لا تنفيذ في هذا المستند  
**الحالة:** مقترح للتنفيذ على مراحل عبر PRs مستقلة  
**المرجع التشغيلي الحالي:** `CLAUDE.md` · `docs/db/*` · `src/pages/routes.tsx` · `src/components/layout/sidebar.tsx`

---

## 1) الخلاصة التنفيذية

Wardah اليوم منتج ERP متعدد المجالات (تصنيع/تكلفة مراحل، مخزون، مشتريات/AP، مبيعات/AR، محاسبة/GL، موارد بشرية، تقارير ورؤى، وإدارة مؤسسة/RBAC)، بينما المستودع والواجهة يعكسان هذا الواقع **جزئيًا فقط**:

| الطبقة | الواقع الحي | الفجوة |
|--------|-------------|--------|
| المنتج في ذهن المستخدم | قوائم جانبية غنية بموديولات كاملة | بعض القوائم أعمق من التنفيذ الفعلي (خصوصًا المبيعات) |
| المستودع | `features/*` + `services/*` ضخمة + طبقات Clean Architecture جزئية | ثلاثة «منازل» للمنطق بدل خريطة واحدة |
| التنقّل والصلاحيات | Sidebar ثابت + `module-permissions` + `route-permissions` | مصادر متعددة غير متزامنة |
| التوثيق | `docs/db` حيّ وقوي؛ `docs/INDEX` وخطط إعادة تنظيم قديمة | فهرس يصف مجلدات غير موجودة |
| الهوية البصرية | shadcn + Tailwind + Wardah glass/gradient | ازدواج مزوّدات ثيم، وتطبيق غير موحّد بين الموديولات |

**الهدف من هذه الخطة:** جعل المستودع والواجهة يعكسان **خريطة منتج واحدة** — ديناميكية، واضحة، واحترافية — دون كسر عقود قاعدة البيانات أو حوكمة الـmigrations، ودون حذف تاريخ محكوم.

## 2) الصورة الحقيقية للمنتج (Product Map)

هذه هي الخريطة المرجعية المقترحة — مصدر واحد لكل من: التنقّل، الصلاحيات، المسارات، وهيكل المجلدات، وفهارس التوثيق.

```
Wardah ERP
├── Dashboard                 لوحة التشغيل
├── Manufacturing             التصنيع وتكلفة المراحل (قلب التمايز)
│   ├── Orders / MES / Capacity / Efficiency
│   ├── Process Costing / EUP / COP / Variance
│   ├── Stages / WIP / Standard Costs / Workcenters
│   └── BOM / Quality
├── Inventory                 المخزون والتقييم وUoM
│   ├── Items / Categories / Movements / Adjustments
│   ├── Valuation / Warehouses / Locations / Bins / Transfers
│   └── UoM engine (قدرة تقنية تحت المخزون، لا موديول تنقّل مستقل)
├── Purchasing (AP)           المشتريات والمطابقة الثلاثية والمدفوعات
├── Sales (AR)                المبيعات والتحصيل (يجب أن يطابق عمق القائمة)
├── Accounting & GL           دفتر الأستاذ والقيود والتقارير المحاسبية
│   └── COA + Journals + TB + Statements + Posting + Reconciliation
├── HR                        الموارد البشرية والرواتب
├── Reports & Insights        تقارير المجال + رؤى/تحليلات
├── Settings                  إعدادات المؤسسة التشغيلية
├── Org Admin (RBAC)          مستخدمون، دعوات، أدوار، تدقيق
└── Super Admin               طبقة المنصة
```

### مبادئ مواءمة الصورة

1. **ما يظهر في الشريط الجانبي يجب أن يكون قابلًا للوصول فعليًا** (مسار + شاشة + صلاحية + خدمة/RPC)، أو يُعلَّم صراحةً كـ Coming soon داخل الكتالوج لا كرابط زائف.
2. **ما هو قوي في المنتج يجب أن يكون قويًا في المستودع** (مثل تكلفة المراحل والمخزون والمشتريات/السندات).
3. **ما هو ضعيف في التنفيذ لا يُضخَّم في الواجهة** حتى يكتمل — أو يُبسَّط التنقّل ليعكس الجاهزية.
4. **RBAC ليس موديولًا تشغيليًا للمستخدم العادي** — يبقى تحت Org Admin، مع ربط واضح في التوثيق والصلاحيات.
5. **UoM والمحرك المالي للتقارير** قدرات تقنية/مخططات — لا تُفرَض كأقسام تنقّل مستقلة إلا إذا صارت تجارب مستخدم مستقلة.

## 3) تشخيص الفجوات (من القراءة الحالية)

### 3.1 واجهة المستخدم والتنقّل

- الشريط الجانبي في `sidebar.tsx` يعرّف شجرة تنقّل غنية يدويًا، مع تكرار `MODULE_CODES` بدل الاستيراد من `config/module-permissions.ts`.
- `MODULE_PERMISSIONS` أضيق من الشريط (خصوصًا التصنيع والمخزون والتقارير) → الصلاحيات والتنقّل غير متطابقين عمقًا.
- المحاسبة معروضة كمجموعة واحدة بينما المسارات منقسمة بين `/accounting/*` و`/general-ledger/*`.
- شارات رقمية زخرفية في الشريط (`badge: '2'/'3'`) لا تعكس بيانات حية.
- مسار routing للتصنيع ما زال موجودًا بينما أُزيل من التنقّل (fail-closed) — يحتاج سياسة واضحة: إخفاء أم إزالة أم إعادة تفعيل.
- بقايا مسارات/أسماء Gemini (`/gemini-dashboard` redirect، خدمات/proxy) تُشوّش صورة المنتج.

### 3.2 هيكل الواجهة الأمامية

```
اليوم (هجين):
  features/<domain>     ← UI أساسي غير موحّد العمق
  services/*            ← طبقة API/RPC مسطحة وكبيرة (~150 ملفًا)
  domain/application/infrastructure  ← Clean Architecture جزئي (تكلفة مراحل/تقييم)
  modules/              ← شريحة CQRS رقيقة
  pages/ + components/  ← أغلفة مشتركة + org/super admin
```

أبرز الانحرافات:

| المجال | التنقّل | المجلد | الملاحظة |
|--------|---------|--------|----------|
| Manufacturing | قوي | `features/manufacturing` كبير | ملفات فهرس ضخمة؛ مكونات مشتركة أيضًا تحت `components/manufacturing` |
| Inventory | قوي | ملفات ضخمة + خدمات عامة | يحتاج تفكيك صفحات |
| Purchasing | قوي | UI رقيق + خدمات سمينة | منطق بعيد عن الواجهة |
| Sales | قوي في القائمة | `features/sales` رقيق جدًا | فجوة مصداقية منتج |
| Accounting/GL | قائمة واحدة | موديولان + خدمات | دمج مفاهيمي مطلوب |
| HR | قوي | أنظف هيكل (`pages/`) | نموذج يُحتذى |
| Reports | قوي | يتضمّن `proxy-service` Node داخل الميزات | حدود غير صحيحة |
| RBAC | Org Admin | `pages/org-admin` + خدمات | مناسب؛ يحتاج توثيق أوضح |

ازدواج إضافي يضعف الاحترافية:

- Auth: `AuthContext` + `auth-store`
- Theme: `ThemeProvider` + `WardahThemeProvider`
- i18n: كتالوج عام + فرع HR مستقل
- منطق مشترك: `components/manufacturing` مقابل `features/manufacturing`

### 3.3 المستودع خارج `src`

- جذر المستودع يحمل ملاحظات تشغيلية (`README_TODAY.md`, `SESSION_SUMMARY.md`, `COMMIT_MESSAGE.md`, `VERCEL_ENV_SETUP.md`, …) خارج `docs/`.
- `js/` تراث موازٍ لـ`src`.
- `wardah_erp_handover/` و`sql/urgent_fixes/` يختلطان بصريًا مع المسار المحكوم (`sql/migrations` + baseline).
- `docs/INDEX.md` (2025-01-20) يصف `getting-started/` و`troubleshooting/` وREADMEs لمجالات غير موجودة على القرص.
- `docs/REPOSITORY_REORGANIZATION_PLAN.md` معلَّم «مكتمل» لكنه يصف هيكلًا طموحًا لم يُستكمل (فهارس الميزات، getting-started).
- `docs/features/` يكاد يكون تصنيعًا فقط رغم تعدد المجالات.
- `docs/db/` هو الأقوى والأصدق — يجب أن يبقى مركز حوكمة DB دون خلطه بخطط UI.

### 3.4 الهوية البصرية والتجربة

- يوجد أساس جيد: `components/ui` (shadcn-style)، `styles/wardah-ui-core.css`، توكنات، ومسار `/design-system`.
- التطبيق غير موحّد: بعض الشاشات «زجاجية/تدرجات»، وأخرى جداول/نماذج تقليدية سميكة.
- الاعتماد على `isRTL` للتخطيط ما زال شائعًا؛ الاتجاه المفضّل: خصائص منطقية (logical) + مفاتيح `t()`.
- صفحات Overview غير متسقة بين الموديولات (بعضها لوحة حقيقية، وبعضها قائمة اختصارات).

## 4) المبادئ التوجيهية (Best Practices لهذه المرحلة)

1. **مصدر حقيقة واحد لخريطة المنتج (Product Catalog)**  
   كائن/ملف إعداد واحد يصف: الموديول، الأيقونة، المسار، الصلاحية، الأبناء، حالة الجاهزية (`ga` | `beta` | `hidden` | `planned`)، ومفتاح الترجمة.
2. **Feature-first للواجهة**  
   كل مجال منتج = `src/features/<domain>/` بهيكل داخلي ثابت، مع إبقاء المكوّنات المشتركة حقًا في `components/`.
3. **الخدمات تتبع المجال**  
   إما نقل تدريجي إلى `features/<domain>/api` أو تجميع `services/<domain>/` بأسماء مطابقة للتنقّل — ممنوع الإبقاء على «محيط مسطح» بلا حدود.
4. **Clean Architecture انتقائية**  
   تُرسَّخ حيث القيمة عالية (تكلفة مراحل، تقييم مخزون، قواعد محاسبية حساسة). لا تُفرض على CRUD البسيط. يُحدَّث ADR-001 ليعكس «selective overlay» بدل ادعاء اكتمال شامل.
5. **DB-first للعقود، UI-second للتجربة**  
   لا تُعاد هيكلة المسارات اعتمادًا على RPC غير مطبّقة؛ ترتيب النشر الحالي في `CLAUDE.md` يبقى ساريًا.
6. **Additive فقط على المخطط**  
   لا حذف migrations/أعمدة/تاريخ؛ إعادة التنظيم للمستودع والواجهة لا تمس سجل Production.
7. **PRs صغيرة ومجال واحد**  
   كل مرحلة قابلة للمراجعة والرجوع؛ لا «Big Bang rename».
8. **الجمال = وضوح معلومات + اتساق بصري + حركة هادفة**  
   ليس إضافة بطاقات وزخارف. كل Overview: غرض واحد، هرمية واضحة، حالة فارغة محترمة، وإجراءات أساسية ظاهرة.

## 5) الهيكل المستهدف

### 5.1 جذر المستودع (نظيف واحترافي)

```
wardah/
├── README.md                 # صورة المنتج الحقيقية + روابط حية فقط
├── CONTRIBUTING.md           # هيكل الميزات + كتالوج المنتج + معايير UI
├── CLAUDE.md                 # حوكمة DB/CI (يبقى المرجع التشغيلي)
├── SECURITY.md
├── CHANGELOG.md
├── docs/
│   ├── INDEX.md              # فهرس حي يطابق القرص
│   ├── architecture/         # ADRs + هذه الخطة + خريطة المنتج
│   ├── db/                   # Runbooks وحوكمة المخطط (لا تُخلط)
│   ├── features/             # README لكل مجال منتج
│   ├── quality/ · security/ · deployment/ · testing/
│   └── archive/              # تاريخ؛ لا روابط افتراضية من INDEX
├── sql/
│   ├── baseline/
│   ├── migrations/           # المصدر القانوني للتغيير الحي
│   └── archive/              # تراث صريح
├── scripts/                  # CI وبوابات فقط (التراث مؤرشف)
├── src/                      # التطبيق
├── e2e/ · tests/
├── supabase/                 # مؤشر إلى sql/migrations فقط
└── public/
```

ما يُنقل لاحقًا من الجذر إلى `docs/` أو `docs/archive/`: ملاحظات الجلسات، إعدادات نشر مؤقتة، SQL فحوص جذرية.  
ما يُعلَّم صراحة «خارج المسار الحي»: `js/`, `wardah_erp_handover/` (README يوضح: ليس runtime).

### 5.2 هيكل الميزة الموحّد (نموذج HR كمرجع جودة)

```
src/features/<domain>/
├── index.tsx                 # تصدير المسارات فقط (خفيف)
├── routes.tsx                # تعريف الأبناء lazy
├── catalog.ts                # اختياري: جزء الكتالوج المحلي إن لزم
├── pages/                    # شاشات المسارات
├── components/               # مكوّنات خاصة بالمجال
├── hooks/                    # React Query hooks للمجال
├── api/                      # عملاء RPC/الاستعلامات (بدل services العامة تدريجيًا)
├── lib/                      # مساعدات خالصة
├── types/
└── __tests__/
```

استثناءات مقصودة:

- `pages/org-admin` و`pages/super-admin` تبقى صفحات منصّة وليست «ميزات تشغيل».
- `components/ui` و`components/layout` و`components/vouchers` مشتركة عابرة للمجالات.
- `domain/application/infrastructure` تبقى لقلب تكلفة المراحل/التقييم؛ الواجهة تستدعيها عبر application services لا عبر SQL مباشر.

### 5.3 كتالوج المنتج الديناميكي

ملف مركزي مقترح:

`src/config/product-catalog.ts`

يملك:

- الشجرة الكاملة (موديول → أبناء)
- `permission` / `moduleCode` / `requireOrgAdmin`
- `status: 'ga' | 'beta' | 'planned' | 'hidden'`
- `navOrder`, `icon`, `i18nKey`, `path`
- اختياريًا: `featureFlag`, `docsPath`

المستهلكون:

| المستهلك | السلوك |
|----------|--------|
| Sidebar | يرسم من الكتالوج بعد تصفية الصلاحيات والحالة |
| Command Palette / بحث سريع (لاحقًا) | نفس المصدر |
| ModuleGuard / route meta | يطابق المسار بالكتالوج |
| `MODULE_PERMISSIONS` | يُشتق أو يُستبدل تدريجيًا |
| Docs generator / INDEX | جدول مجالات من نفس الأسماء |

النتيجة: تغيير واحد يحدّث التنقّل والصلاحيات الظاهرة وحالة الجاهزية — ديناميكيًا وبلا تكرار.

## 6) خطة الواجهة: ديناميكية، جميلة، احترافية

### 6.1 معمارية التجربة (IA)

1. **شريط جانبي مولَّد من الكتالوج**  
   - مجموعات قابلة للطي بحالة محفوظة في `ui-store`.  
   - إخفاء العناصر `planned/hidden`.  
   - شارات حيّة فقط (عدد مسودات، تنبيهات تباين، مستحقات) عبر hooks صغيرة — لا أرقام ثابتة.
2. **Page Shell موحّد لكل مجال**  
   - `PageHeader` (عنوان + وصف قصير + إجراءات أولية)  
   - شريط سياق المؤسسة/الفترة عند الحاجة  
   - `EmptyState` / `LoadingState` / `ErrorState` من `components/ui`
3. **Overview لكل موديول = «غرفة قيادة» لا قائمة روابط**  
   - 3–5 مؤشرات أو مهام متكررة  
   - اختصارات للمسارات الفرعية المصرّح بها فقط  
   - لا بطاقات زخرفية بلا وظيفة
4. **المحاسبة كتجربة واحدة**  
   - الإبقاء على مسارات GL إن لزم تقنيًا، لكن التنقّل والتسمية والـbreadcrumb تحت مظلة «المحاسبة / دفتر الأستاذ».
5. **المبيعات**  
   - إما تعميق التنفيذ ليطابق القائمة، أو تقليص القائمة مؤقتًا إلى ما هو GA — الخيار الثاني أصدق للمستخدم حتى تكتمل الشاشات.

### 6.2 النظام البصري

| القرار | التفصيل |
|--------|---------|
| مصدر الثيم | توحيد على مزوّد واحد + توكنات CSS (`--wardah-*`) |
| المكوّنات | الإبقاء على shadcn primitives؛ تجنّب أنماط زجاجية على الجداول الكثيفة |
| الحركة | 2–3 حركات هادفة: انتقال الصفحة، فتح المجموعات، ظهور الحالات الفارغة — بلا ضوضاء |
| RTL | `dir` على المستند + logical properties؛ إيقاف تفرعات نص عربي/إنجليزي في JSX |
| الكثافة | جداول تشغيلية denser؛ لوحات Overview أرحب |
| اللون | الالتزام بهوية Wardah الحالية بعد تنظيف التدرجات العشوائية لكل شاشة |

مسار `/design-system` يصبح **عقد قبول بصري**: كل مكوّن جديد يظهر هناك قبل التعميم.

### 6.3 الاتساق اللغوي

- مفاتيح تنقّل مركزية تحت `navigation.*` و`modules.<code>.*`
- دمج فرع HR i18n تدريجيًا في الكتالوج العام
- بوابة CI الحالية ضد النمط legacy تبقى؛ تُوسَّع لاحقًا لفحص مفاتيح الكتالوج الناقصة

## 7) خطة تنظيم المستودع (مراحل تنفيذ)

> كل مرحلة = PR واحد أو سلسلة PRs صغيرة. لا يُدمج UI يعتمد على عقد DB قبل تطبيق الـmigration (إن وُجدت).

### المرحلة 0 — تجميد الصورة (أسبوع 0، بلا كسر)

- [ ] اعتماد «خريطة المنتج» في §2 كمرجع فريق (ADR قصير أو تحديث README architecture).
- [ ] جرد مسارات `routes.tsx` × عناصر `sidebar` × مفاتيح صلاحيات → جدول فجوات (GA / partial / nav-only).
- [ ] تحديث `docs/INDEX.md` ليحذف الروابط الميتة ويشير إلى الملفات الحية فقط (`docs/db`, manufacturing, quality, architecture).
- [ ] تعليم `docs/REPOSITORY_REORGANIZATION_PLAN.md` كـ historical / superseded والإشارة إلى هذه الخطة.

**مخرجات:** جدول فجوات + فهرس حي. لا نقل ملفات بعد.

### المرحلة 1 — كتالوج المنتج الديناميكي (الأولوية القصوى للواجهة)

- [ ] إنشاء `product-catalog.ts` بمحتوى مطابق للتنقّل الحالي + `status` لكل عنصر.
- [ ] تحويل Sidebar ليستهلك الكتالوج + الصلاحيات.
- [ ] إزالة تكرار `MODULE_CODES` المحلي والشارات الزخرفية.
- [ ] مواءمة `module-permissions` / اشتقاقه من الكتالوج.
- [ ] اختبارات: عناصر مخفية بلا صلاحية؛ عناصر `planned` لا تُعرض؛ المحاسبة تظهر كمجموعة واحدة.

**مخرجات:** تنقّل ديناميكي = صورة المنتج المعتمدة.

### المرحلة 2 — هيكل الميزات دون تغيير سلوك

ترتيب مقترح حسب العائد/الخطر:

1. **Sales** — إما تقليص Nav إلى GA أو تفكيك/بناء الصفحات لتطابق القائمة (قرار منتج صريح في PR).
2. **Accounting + General Ledger** — توحيد التسمية والتجربة؛ الإبقاء على المسارات إن لزم مع aliases/breadcrumbs موحّدة.
3. **Purchasing** — تقريب الخدمات إلى `features/purchasing/api` دون تغيير العقود.

## 10) معايير قبول النجاح

تُعتبر المواءمة ناجحة عندما:

1. **خريطة واحدة:** الشريط الجانبي والصلاحيات الظاهرة و`docs/features` تستخدم نفس أسماء المجالات والمسارات.
2. **صدق التنقّل:** لا رابط في الشريط يؤدي إلى شاشة فارغة/placeholder غير معلنة؛ كل `ga` يعمل.
3. **مستودع قابل للشرح في دقيقة:** `features/<domain>` ≈ ما يراه المستخدم؛ `docs/db` ≈ ما يحكم البيانات؛ `services` أو `features/*/api` ≈ كيف تُستدعى العقود.
4. **واجهة متسقة:** نفس Page Shell وحالات التحميل/الفراغ/الخطأ عبر المجالات الأساسية؛ ثيم واحد؛ RTL منطقي.
5. **توثيق غير كاذب:** `docs/INDEX.md` بلا روابط ميتة؛ README يصف المنتج الفعلي لا الهيكل الطموح القديم.
6. **CI يحمي الصورة:** انحراف الكتالوج عن المسارات أو المفاتيح يظهر في الفحص.

## 11) اقتراح ADR مختصر (للمرحلة 0/1)

**العنوان المقترح:** ADR-004 — Product Catalog as Single Source of Navigation & Module IA  

**القرار:** اعتماد كتالوج منتج مُصدَّر من الإعدادات كمصدر وحيد للتنقّل وحالة الجاهزية وربط الصلاحيات الظاهرة، مع إبقاء حوكمة DB في `docs/db` و`CLAUDE.md` منفصلة.  

**العواقب:** إزالة تعريفات الشريط اليدوية المكررة؛ تمكين بحث/overview ديناميكي لاحقًا؛ إجبار قرارات صريحة لحالة كل مسار (`ga`/`planned`).
