## 4. Failure-stop rules
- Stop at the first non-success: a migration error, a missing/duplicate ledger row, a hash or pin mismatch, an unexpected NOTICE, or any business-row drift outside §3.7. Do not apply the next step.
- After **any** tool result other than a clean, expected success, read both sides before anything else: the ledger (§3.1/§3.2) **and** the catalog. The possible states, with the tool's transaction behavior [UNVERIFIED], are:

| Ledger row | Catalog changed | Reading | Action |
|---|---|---|---|
| none | no | file refused/rolled back (its own `COMMIT` not reached) | report; no retry without Codex/owner |
| present, hash equal | yes, §3 postflight passes | success | continue |
| none | **yes** | the file's `COMMIT` landed but the tool did not record it (error, timeout or lost response after commit) | **hole**: stop; do not re-send the file (it would refuse or double-apply), do not insert a row; owner decides with Codex input |
| present | no / partial | row without effect | stop; owner and Codex |
| present, hash or `n_statements` wrong | yes | wrong bytes were committed | stop; treat as drift; owner and Codex |

  A hole cannot be repaired by editing the ledger (CLAUDE.md). Whether a documented exception, a restore of B0/B1, or a forward-fix applies is a decision to be made **before the window**, not during it.
- A refused file is atomic **by its own `BEGIN … COMMIT`** (fingerprint-tested in the acceptance suites): verify no ledger row and an unchanged catalog, then report. No retry, no edit of an applied or merged file, no ad-hoc SQL fix in the target. A fix is a new reviewed, additive migration.
- If the stop falls between 195 and 203, the direct WIP-create failure (G6) persists until the plan resumes or the owner restores. The executor does not choose a different order. Applying 203 out of order is allowed only if the owner's release named order (3) of §1 beforehand and the stop leaves the catalog in exactly the state that order reached; otherwise the options are to resume the fixed order or restore B0/B1. Restore vs forward-fix is the owner's decision with Codex input.
- Intermediate states are real and persist between calls: each file is its own transaction, so a stop at any step leaves the earlier steps committed. Besides the WIP break above, 195 alone leaves MO/WO/reservation maintenance disabled (G9), and 199–201 without 202 leaves QC's `service_role` direct-INSERT path open (§1).
- Never touch `supabase_migrations.schema_migrations` to make a state look consistent.
