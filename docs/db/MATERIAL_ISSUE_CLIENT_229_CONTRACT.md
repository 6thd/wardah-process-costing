## Canonical client command

Use only `rpc_consume_material_event(p_mo_id uuid,p_stage_id uuid,p_event_id uuid,p_consumptions jsonb)`. The actor and organization are resolved and enforced by the DB; the client must not supply or trust an org in the mutation payload. The UI selects one explicit MO and stage and one or more ordered lines. Every line explicitly supplies `item_id`, `reservation_id`, `warehouse_id`, `work_order_id`, `uom_id`, a positive JSON-number `quantity` at no more than six decimal places, `consumption_type: "MANUAL"`, and optional string/null `notes`. Never send unknown keys or client unit cost/total cost. The service validates shape for usability; the RPC remains authoritative for membership, permission, lifecycle, policy, stock, UoM, quantity and price.

The UI lists only selectable data from the same target MO and organization, including an explicit WO. It shows effective allowed WO states from `rpc_get_material_issue_wo_statuses`, and marks the default `IN_PROGRESS` clearly. It must fail closed when MO/stage/reservation/WO/warehouse/UoM or policy reads fail, are partial, stale after an org switch, or are ambiguous. Do not silently choose a WO or substitute a warehouse. UI filters are guidance, not authorization: the DB checks every supplied reference and the live policy. Display the returned `event_id`, server-derived counts and cost only after a successful RPC acknowledgment.

## Stable event and unknown-outcome handling

Generate one UUID for **one immutable complete batch** when the operator confirms a valid selection. Before the first network call, durably persist `event_id`, user ID, target org ID, MO, stage, the exact ordered JSON line payload and a pending state in storage that survives a page reload in the same browser (for example IndexedDB). If durable persistence fails, do not send. Keep the byte-equivalent business request and ID for all retries, including browser reload and lost-response recovery; serialization may reorder JSON object keys but may not change line order, actor, any business field, or a numeric value. Do not re-read and rebuild the submitted payload from current reservations, policy or stock on retry.

A timeout, disconnected browser, navigation or unknown response leaves the attempt **pending**. On return, display the pending event under the same user and organization, with the exact payload read-only; retry the same RPC with the same ID and payload. A retry can return the stored result even after MO completion, closed WIP or exhausted reservation. A changed policy does not justify editing a pending event. Do not report failure as proof of rollback after a network error. Do not generate another ID for a button double-click, React remount, automatic retry, page reload or tab switch. Disable parallel submissions of the same draft and coordinate two tabs on the same browser; the DB event lock is the final concurrency authority.

Only a confirmed successful response with the matching `event_id` clears pending. A server-returned conflict is shown as a conflict, never silently retried with a new ID. A named authorization or validation denial is shown without claiming an effect was committed; preserve the attempt until the operator explicitly resolves it. If an outcome cannot be resolved by an identical retry, retain it for support/reconciliation rather than expiring or discarding it and creating a new event. The client does not directly read the private receipt table. A genuinely new partial consumption, even on the same reservation, is a separately confirmed draft with a new ID **after** the earlier attempt is resolved. Document same-browser durability limits; do not claim cross-device recovery.

The response is not a generic optimistic mutation: verify `success === true`, matching event/MO/stage and a coherent `consumption_ids`/`consumption_count` before showing committed success. Invalidate stock, reservations, consumption and stage-WIP queries only after acknowledgment, and re-read authoritative values. Avoid retry libraries that recreate the UUID or payload in each invocation.

## Permission and placement

Mount a manual material-issue action in the manufacturing MO/work-order context, with explicit stage and WO selection. The employee action appears only after permissions finish loading and the exact `manufacturing.material_consumption.consume` key is present; a missing/stale UI snapshot never grants authority. Refresh permission and organization context on relevant focus/org changes; a server denial still wins immediately after a revocation. Org Admin bypass is decided by `has_permission` in the DB, not by a client-side assumption. The RBAC role editor must display the exact existing key under manufacturing so the Org Admin can assign it to an employee. Do not require an unrelated orders-update permission just to consume, and do not treat a read permission as consume authority.

Add a manufacturing settings control for the **existing** WO policy RPCs. The effective choices are exactly `IN_PROGRESS` (required), plus optional `READY` and `IN_SETUP`. Load `rpc_get_material_issue_wo_statuses` for the current org; show version and current states. An active same-org Org Admin may submit one of the four canonical ordered arrays through `rpc_set_material_issue_wo_statuses`; the RPC performs authorization, locking, version increment and audit. Ordinary employees may read the effective states but may not edit. Fail closed on a failed/partial read, avoid saving a default over an unread policy, and re-read after a successful save. Concurrent admin-to-admin settings edits are currently last-writer-wins because the RPC has no expected-version argument; show the refreshed version and do not claim optimistic concurrency. Any requirement to reject stale admin saves needs a separate DB migration and review.

## Required acceptance for the consumer PR

1. **Mounted browser path with real identities in an isolated environment:** active Org Admin assigns the exact key using the existing RBAC UI; same-org employee sees and can submit the manual action. Ungranted, revoked, expired/inactive-role, inactive membership and other-org employees cannot submit; a stale visible button gets a DB denial. Test organization switching while data loads and a user belonging to two organizations.
2. **Lost-response control:** the server commits one partial batch but the browser loses the response. Reload the page; the same user's pending event shows the original immutable payload. Retry returns the stored result with the **same** event ID and exactly one set of SLE/bin, reservation, consumption, receipt and WIP effects. With the persistence layer disabled, or UUID regenerated during retry, this test must fail.
3. **Other retry cases:** double click, two tabs, a deliberate second event on the same reservation, concurrent same-ID requests, same ID with changed line/actor/MO, network failure before commit, and replay after lifecycle/policy changes. Assert DB effects and errors, not only number of mocked RPC invocations. Do not conflate a genuine second event with a retry.
4. **Input and failure path:** missing explicit WO/stage/warehouse/UoM, invalid quantity/line, failed policy/catalog read, org switch, conflict, revoked permission, and partially completed UI fetch all block or fail without a new server effect. A multi-line second-line failure leaves no effect. A failed settings read cannot save a default. A settings update accepts the four canonical arrays, increments the version/audit, and does not widen the MO rule.
5. **Retired paths:** code search plus mounted tests prove no UI invokes direct INSERT, retired v1/v2/array signatures or backflush; explicitly exercise old services/hooks as retired or migrated. Test that a permission-aware employee UI does not silently fall back when M192 RPC is unavailable.
6. **Gates:** type-check, focused unit/integration, exact-head CI, i18n/accessibility for the Arabic UI, and a real PostgreSQL 17/Supabase session test of the M192/M193 effect and authorization contract. Keep Production untouched by fixtures and keep the operational hold until separate owner acceptance.
