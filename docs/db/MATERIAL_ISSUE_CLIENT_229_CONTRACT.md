## Canonical client command

Use only `rpc_consume_material_event(p_mo_id uuid,p_stage_id uuid,p_event_id uuid,p_consumptions jsonb)`. The actor and organization are resolved and enforced by the DB; the client must not supply or trust an org in the mutation payload. The UI selects one explicit MO and stage and one or more ordered lines. Every line explicitly supplies `item_id`, `reservation_id`, `warehouse_id`, `work_order_id`, `uom_id`, a positive JSON-number `quantity` at no more than six decimal places, `consumption_type: "MANUAL"`, and optional string/null `notes`. Never send unknown keys or client unit cost/total cost. The service validates shape for usability; the RPC remains authoritative for membership, permission, lifecycle, policy, stock, UoM, quantity and price.

The UI lists only selectable data from the same target MO and organization, including an explicit WO. It shows effective allowed WO states from `rpc_get_material_issue_wo_statuses`, and marks the default `IN_PROGRESS` clearly. It must fail closed when MO/stage/reservation/WO/warehouse/UoM or policy reads fail, are partial, stale after an org switch, or are ambiguous. Do not silently choose a WO or substitute a warehouse. UI filters are guidance, not authorization: the DB checks every supplied reference and the live policy. Display the returned `event_id`, server-derived counts and cost only after a successful RPC acknowledgment.

## Stable event and unknown-outcome handling

Generate one UUID for **one immutable complete batch** when the operator confirms a valid selection. Atomically check for and create the pending record in one IndexedDB readwrite transaction with a unique unresolved slot keyed by `(user_id, mo_id)` (the target MO's identity, never a mutable UI org selector). This transaction must reject a new draft if any sent or unresolved attempt already occupies that slot, including one created by another tab. Use a browser lock as additional coordination where available, but never depend on a non-atomic localStorage check. Persist `event_id`, user ID, target org ID, MO, stage, the exact ordered JSON line payload and pending/sent state **before** the first network call; storage or coordination failure blocks sending. A second tab may inspect/retry the same immutable event, but cannot allocate another ID for that MO. Document browser-storage eviction limits; request durable storage where supported without claiming it is guaranteed or cross-device. Keep the byte-equivalent business request and ID for all retries, including browser reload and lost-response recovery; serialization may reorder JSON object keys but may not change line order, actor, any business field, or a numeric value. Do not re-read and rebuild the submitted payload from current reservations, policy or stock on retry.

A timeout, disconnected browser, navigation or unknown response after sending leaves the attempt **unknown** and occupies the unresolved MO slot. On return, display the event under the same user and organization with its exact payload read-only; retry the same RPC with the same ID and payload. With active membership and permission, a replay can return the stored result after MO completion, closed WIP or exhausted reservation; revoked permission or inactive membership is rejected **before** the receipt lookup and does not establish whether the earlier send committed. A changed policy does not justify editing a pending event. Do not report failure as proof of rollback after a network error. Do not generate another ID for a button double-click, React remount, automatic retry, page reload or tab switch. The DB event lock is the final authority for same-ID concurrent calls.

Only a confirmed successful response with matching `event_id` clears an unknown attempt automatically. A conflict is shown without minting a new ID. Any later authorization, membership, malformed-input or other pre-receipt denial is **not** evidence that the first send rolled back; it cannot clear the unresolved slot, even when the operator clicks Dismiss. If identical retry cannot return the stored result, only a trusted server-side reconciliation of `wardah_internal.material_issue_events` by the MO-derived `(org_id,event_id)`, with actor and request fingerprint checked and an auditable support decision, may mark the unknown attempt committed or definitively absent. An ordinary operator cannot self-resolve unknown state, and the browser cannot directly read the private receipt table. A never-sent local draft or an acknowledged server rejection proven to precede any send may be discarded separately. A genuinely new partial consumption, even on the same reservation, requires the previous sent attempt to be resolved first; otherwise no new ID is allocated. Document that same-browser storage can be evicted and that cross-device recovery requires support reconciliation, not an automatic new event.

The response is not a generic optimistic mutation: verify `success === true`, matching event/MO/stage and a coherent `consumption_ids`/`consumption_count` before showing committed success. Invalidate stock, reservations, consumption and stage-WIP queries only after acknowledgment, and re-read authoritative values. Avoid retry libraries that recreate the UUID or payload in each invocation.

## Permission and placement

Mount a manual material-issue action in the manufacturing MO/work-order context, with explicit stage and WO selection. The employee action appears only after permissions finish loading and the exact `manufacturing.material_consumption.consume` key is present; a missing/stale UI snapshot never grants authority. Refresh permission and organization context on relevant focus/org changes; a server denial still wins immediately after a revocation. Org Admin bypass is decided by `has_permission` in the DB, not by a client-side assumption. The RBAC role editor must display the exact existing key under manufacturing so the Org Admin can assign it to an employee. Do not require an unrelated orders-update permission just to consume, and do not treat a read permission as consume authority.

Add a manufacturing settings control for the **existing** WO policy RPCs. The effective choices are exactly `IN_PROGRESS` (required), plus optional `READY` and `IN_SETUP`. Load `rpc_get_material_issue_wo_statuses` for the current org; show version and current states. An active same-org Org Admin may submit one of the four canonical ordered arrays through `rpc_set_material_issue_wo_statuses`; the RPC performs authorization, locking, version increment and audit. Ordinary employees may read the effective states but may not edit. Fail closed on a failed/partial read, avoid saving a default over an unread policy, and re-read after a successful save. Concurrent admin-to-admin settings edits are currently last-writer-wins because the RPC has no expected-version argument; show the refreshed version and do not claim optimistic concurrency. Any requirement to reject stale admin saves needs a separate DB migration and review.

## Required acceptance for the consumer PR

1. **Mounted browser path with real identities in an isolated environment:** active Org Admin assigns the exact key using the existing RBAC UI; same-org employee sees and can submit the manual action. Ungranted, revoked, expired/inactive-role, inactive membership and other-org employees cannot submit; a stale visible button gets a DB denial. Test organization switching while data loads and a user belonging to two organizations.
2. **Lost-response control:** the server commits one partial batch but the browser loses the response. Reload the page; the same user's pending event shows the original immutable payload. Retry returns the stored result with the **same** event ID and exactly one set of SLE/bin, reservation, consumption, receipt and WIP effects. With persistence disabled, UUID regenerated during retry, or the unresolved-slot atomic check removed, the corresponding negative-control test must fail. Simulate a first committed send followed by permission revocation: pre-receipt denial on replay leaves the slot unknown and prevents a new event until audited server reconciliation.
3. **Other retry cases:** double click, two tabs opened before the first send (both confirm the same MO, exactly one ID allocated by the atomic unresolved-slot transaction), a deliberate second event on the same reservation only after resolution, concurrent same-ID requests, same ID with changed line/actor/MO, network failure before commit, and replay after lifecycle/policy changes. Assert DB effects and errors, not only number of mocked RPC invocations. Do not conflate a genuine second event with a retry.
4. **Input and failure path:** missing explicit WO/stage/warehouse/UoM, invalid quantity/line, failed policy/catalog read, org switch, conflict, revoked permission, and partially completed UI fetch all block or fail without a new server effect. A multi-line second-line failure leaves no effect. A failed settings read cannot save a default. A settings update accepts the four canonical arrays, increments the version/audit, and does not widen the MO rule. A stale mounted WIP form loaded before a posted event must be unable to reset `cost_material` or change protected eligibility fields; test the DB denial or guarded RPC and unchanged effects under #278.
5. **Retired paths:** code search plus mounted tests prove no UI invokes direct INSERT, retired v1/v2/array signatures or backflush; explicitly exercise old services/hooks as retired or migrated. Test that a permission-aware employee UI does not silently fall back when M192 RPC is unavailable.
6. **Gates:** type-check, focused unit/integration, exact-head CI, i18n/accessibility for the Arabic UI, and a real PostgreSQL 17/Supabase session test of the M192/M193 effect and authorization contract. Keep Production untouched by fixtures and keep the operational hold until #278 and relevant #170/#154 protections have independent live readbacks and separate owner acceptance.
