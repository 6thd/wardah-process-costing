| 1 | The MCP `apply_migration` tool is `applyMigration(projectId, {name, query})` → `POST /v1/projects/{ref}/database/migrations` with body `{name, query}`. If the migration failed, it will throw an error"), so `success=true` in the Production records carries no response data. | DOC (supabase-mcp source) |
| 2 | `execute_sql` is a **different endpoint**: `POST /v1/projects/{ref}/database/query` with `{query, parameters, read_only}`. There is also `POST …/database/query/read-only` ("Run a sql query as supabase_read_only_user"). A role seen via `execute_sql` says nothing about `apply_migration`. | DOC (source + OpenAPI) |
| 3 | The OpenAPI entry for apply-a-migration has no description: body `{query (required), name, rollback}`, optional header `Idempotency-Key` ("ensure the same migration is tracked only once"; the MCP tool does not send it). The migration-detail response has `statements: string[]`, `rollback`, `created_by`, `idempotency_key`. Sibling endpoints exist that must **not** be used here: `PUT …/database/migrations` ("Upsert a database migration without applying", i.e. a ledger-only write) and `DELETE …/database/migrations?gte=` ("Rollback database migrations and remove them from history table"). | DOC (OpenAPI) |

The same page says the endpoint is limited to selected customers. | DOC (verbatim text obtained through a summarizer; re-verify) |
| 5 | Dashboard SQL editor queries "execute as `postgres`". Nothing about this endpoint. | DOC |
| 6 | **A handler exists in Studio, but it is a self-hosted one.** The reviewer's first search missed it (it matched file contents, not the path-routed file). The local agent found, and the reviewer then read, `apps/studio/pages/api/v1/projects/[ref]/database/migrations.ts` (GET and POST; POST calls `applyAndTrackMigrations` in `apps/studio/lib/api/self-hosted/migrations.ts`, which calls `assertSelfHosted()`). It does not write `created_by`, `idempotency_key` or `rollback`. **It is not shown to be the hosted Management API handler.** The role is whatever postgres-meta connects as; the file was not followed further (`./query`, `./util`). | DOC (reference implementation); not the hosted handler |
| 7 | The Supabase CLI's mechanism as read (`apps/cli-go/pkg/migration`) splits a file into statements and would store several `statements` elements. | 9 | Because each of 195–203 ends in its own `COMMIT`, a ledger row written separately by the service would be outside that transaction unless the service rewrites or parses the file (inference); the Studio reference design has exactly that shape (the insert follows the file's `COMMIT` in the same request). With a tool-side `BEGIN` wrapper the file's `BEGIN` and the tool's `COMMIT` raise warnings and the file's `COMMIT` ends the wrapper. | LOCAL emulation of hypotheses (reviewer-side log in the review package, not in the repository); inference |

## 2. What is not established
Two separate open items:
- **Execution-role compatibility (plan gate G8, must be proven before any target action):** the role that executes `apply_migration` (and whether it differs from the `execute_sql` role or from the dashboard role).
- **Ledger/catalog atomicity (plan gate G11, an owner decision, may be an accepted risk):** how the *hosted* service records the ledger row relative to the file's own `COMMIT`; what it does on failure after commit; how it sets `created_by`/idempotency values. The Studio reference suggests the insert follows the file's commit, which is not proof for the hosted service.
- Byte-exact transmission of a large `query` through the MCP wrapper (the historical rows were compared by the local agent; see section 4).
