## Immediate integrity dependency: reproduced deletion and cross-org TRUNCATE

**Confirmed on a disposable PG17.11 database through M192, not on Production:** a same-org member with only `manufacturing.orders.read` deleted one WO with POSTED material consumption. PostgreSQL's `ON DELETE CASCADE` removed the consumption row; the M192 receipt still held its `consumption_ids`, the SLE and bin movement remained, and WIP `cost_material` and reservation `quantity_consumed` remained. With `allow_zero_cost`, completing that MO afterward booked zero cost and no GL entry; an otherwise identical completion without deletion booked the consumed cost. This behavior was tested with a Supabase identity shim, not via PostgREST. A UI delete button is not required for the database path to exist.

Direct MO deletion with the posted consumption present was rejected by FK `23503`, including for a privileged local actor. A **WO DELETE followed by MO DELETE** succeeded for the same read-only member: consumption, WIP and reservations disappeared but the receipt and SLE/bin effects remained. An inactive member's WO deletion raised `NOT_ORG_MEMBER` from an unrelated work-center-load trigger, not a deliberate deletion guard. Anon was rejected `42501`; neither incidental rejection proves posted-consumption protection. The live permission key `manufacturing.orders.delete` is not checked by the current direct-delete route.

The reviewer also ran `TRUNCATE stage_wip_log` as a read-only member on disposable PG17: it erased another organization's WIP rows because TRUNCATE bypasses RLS. Anon could `TRUNCATE labor_time_tracking` in that setup. These are SQL-level tests; PostgREST does not directly expose TRUNCATE, but direct SQL and callable functions warrant revocation. Live catalog grants, policies and FKs matched the fixture in the review's read-only Production comparison; Production then had no posted consumption/event/WO rows.

**Immediate operational gate:** no new `rpc_consume_material_event` call or other M192 material-issue event on Production, including by an Org Admin or pilot, until a dedicated protective migration blocks destructive WO deletion, revokes unsafe DELETE/TRUNCATE grants and passes a live postflight readback. M192 is already live; this holds *new events*, not the migration itself. Do not delete affected WO/MO rows. The absence of events is a dated observation, not a permanent invariant.

The first implementation PR must protect POSTED and any other financially effective consumption **before** a WO delete can cascade; preserve reservation and WO history, block the two-step WO→MO route and decide a narrow audited administrative deletion model. The guard must return its own named error and SQLSTATE so a test cannot pass on an unrelated FK, trigger or RLS denial. Remove client DELETE/TRUNCATE grants and policies in that **first migration**, outside the later compatibility interval, and check all dependent tables and column grants. On PG17 recreate the posted issue; assert guard-specific failure on direct WO deletion and attempted WO→MO sequence, and unchanged receipt IDs, consumption, SLE, bin, WIP, reservation, subsequent completion cost and GL. Verify cross-org WIP and labor history survives attempted TRUNCATE. Test a privileged/indirect delete separately without accepting an incidental authentication-trigger rejection as proof. No Production application without fresh backup, owner approval and independent review.

## Authority and observed write surfaces

The active same-org Org Admin may grant exact permissions through the RBAC UI; an employee receives only explicitly assigned operations. Check membership activity, role expiry, organization ownership, lifecycle, amounts and audit at the database transaction boundary. Org Admin bypass may pass authorization but never structural or lifecycle checks. `service_role` stays server-only. Existing `manufacturing.orders.create` / `.update` do not authorize the new operations by implication.

The independent 2026-09-28 catalog review reports: `authenticated` has INSERT, UPDATE, DELETE and TRUNCATE on `material_reservations`, `work_orders`, `stage_wip_log` **and `manufacturing_orders`**; `anon` has full DML, including TRUNCATE, on reservations, work orders and manufacturing orders, but no table grants on stage WIP. Both `anon` and `authenticated` have mutation and TRUNCATE grants on the WO child tables `labor_time_tracking`, `operation_execution_logs` and `quality_inspections`. No PUBLIC table grants were found. Revoke unnecessary TRUNCATE on WIP and WO child tables in the first protective migration; RLS cannot constrain it. Recheck table, column, inherited and default grants at implementation time. RLS on the first three public manufacturing tables is `TO public`. WO policies accept an inactive membership row; reservation and MO policies use `auth_org_id()` (a `LIMIT 1` selector with no order), whereas stage WIP uses `wardah_org_id()`. Absent an explicit `WITH CHECK`, PostgreSQL reuses `USING` for applicable updates. A grant or zero-row mutation alone establishes neither permission nor denial. A user in two organizations without a trusted org selection must fail closed; derive scope from the target MO and validate every child org.

## Binding lock and permission rules

For every writer touching an **existing** MO and its children, derive the organization from the target MO, validate it, lock the MO `FOR UPDATE` **before** any WO, stage WIP, reservation, product or bin lock, and revalidate scope after locking. Creation of a **new** MO (for example `rpc_create_mo_with_reservation`) may lock a product/bin before inserting that new MO because no existing MO row is available to lock; this exception never permits child writes to an existing MO without first locking that MO. A batch such as `release_expired_reservations` must lock affected MOs in stable `ORDER BY mo_id` order before child reservations and derive scope for each. For M192 events only, take the `(MO-derived org_id,event_id)` event advisory lock **before** MO; then policy `FOR SHARE`, WO, stage WIP, reservations, products, bins in M192's order. Reserve, release, WO start/complete and status transitions must conform to the same MO-first child prefix. In particular, reservation INSERT FK checks on the MO and WO UPDATE triggers must not establish product→MO or WO→MO waits. Rewrite or neutralize the `work_orders.trigger_update_mo_status` path together with #230; merely adding permission checks to `start_operation` and `complete_operation` is insufficient. Exercise real two-session commit and rollback races: reserve vs consume, release vs consume, WO start/complete vs consume, two starts on one WO, and policy change vs consume. Assert actual wait relation and no `40P01`, double effects, stale overwrite or partial pause.

A new permission row is created with **zero explicit `role_permissions` rows**, but this alone does not prove least privilege: `create_role_from_template` matches keys by `LIKE`; the `production_manager` template's `manufacturing.%` would include later manufacturing keys, and Org Admin bypass applies to nonsensitive keys. Existing `Full Access` already includes the M190 consume key in the reviewed organization. Decide and test template behavior for new roles, whether terminal and WIP-cost keys are sensitive, and the Org Admin bypass before selecting key names. Test a new role created from every affected template; test existing roles separately. Do not silently grant via a template or infer authority from `manufacturing.orders.create/update`.

## Migration and rollout gates

1. Before any new Production material-issue event, prove and apply the independent WO-delete and cross-org TRUNCATE protection described above; require live grant/guard readback and retain the operational hold until it passes. Take a fresh inventory of direct writers, callable RPCs (including owner/security mode and EXECUTE ACL), triggers, FK cascades, grants on all columns and effective RLS `USING`/`WITH CHECK`. Prioritize the posted-consumption deletion guard as its own first protective migration with an independent review and PG17 proof, rather than waiting for all employee UI or #260.
2. Write failing PG17 acceptance on **valid populated rows**. Cover direct INSERT/UPDATE/DELETE/TRUNCATE and FK cascades, plus two-step WO→MO deletion; require the *new guard's own* SQLSTATE/reason and unchanged effects, including subsequent completion cost and GL (an unrelated `23503`, `42702`, RLS zero rows or trigger denial does not pass). Cover active Org Admin with invalid input, granted/ungranted employees, inactive membership, inactive/expired role, revoked grant, foreign org and mismatched child→MO org, two-org user without org claim, and historical released reservations. Check `has_table_privilege` / `has_column_privilege` for effective INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES and TRIGGER; use behavioral tests too.
3. Introduce exact keys and guarded RPCs with pinned `search_path`, explicit EXECUTE revokes from PUBLIC/anon and from authenticated for internal helpers, actor/org checks, mandatory MO-first locks and audit entries. New callable RPCs get only the intended `authenticated` EXECUTE. The direct-write closure must revoke `INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER` from PUBLIC, anon and authenticated where applicable and remove permissive policies/column grants; keep reviewed read needs. Do not alter M190–M192 bytes.
4. Enumerate and migrate each caller before revoking its old grant: `inventory-transaction-service.ts` reserve/release and retired consume, `mesService.ts` pause and stale direct consume, `updateWorkOrderStatus`, `stageWipLogService` create/update and `supabase-service.ts` close/delete, MO create/transition paths. Include tests for Admin granting/revoking, employee behavior and event-id retry. DELETE and TRUNCATE revocation for posted-consumption integrity belongs to the first protective migration and has no compatibility exception: no caller requires these grants today. For remaining INSERT/UPDATE writes only, a DB-first compatibility interval, if needed, lasts **at most one reviewed client release** between additive RPC deployment and a dedicated grant-revocation migration; no new user-facing capability during that interval. Both deployments require dated checkpoints. Exit only after an auditable observation window on the deployed client release (versioned API request logs per retired RPC or attributable `pg_stat_statements`/database logs, with an explicit period and zero old-path calls), browser tests and PG17 gates pass, and the revocation migration is deployed and verified. If monitoring cannot attribute old calls or traffic is insufficient, keep the UI unavailable and fail the exit gate. If the exit gate fails, stop rollout and retain the old UI disabled; do not treat an open grant as steady state.
5. Require exact-head Fresh DB on PG17 with M190–M192 acceptance, concurrency tests, actual DELETE cascade negative control, SQLSTATE checks and independent review. Each Production migration needs a current backup, readback and owner approval; employee consumption stays unmounted until real same-org employee-session permission and replay tests pass.
