## Lifecycle and replay

- **Approved MO rule:** only a stored MO status of exactly `in_progress` permits a new event. Reject `draft`, `pending`, `confirmed`, `quality_check`, `on_hold`, `done`, `cancelled`, NULL and all other statuses. Lock the MO in the effects transaction; use NULL-safe comparisons so SQL three-valued logic cannot pass NULL. Input status normalization cannot broaden this rule.
- **Configurable WO rule (owner-requested direction):** use a **dedicated organization-scoped policy table in a private schema**, not `org_settings` (whose existing direct-write policy and grants lack value validation). Seed one row for every existing organization, and create one for each new organization in the DB transaction; require a postflight count of missing/duplicate rows. Default exactly `{IN_PROGRESS}`; an Org Admin may explicitly enable `READY` and/or `IN_SETUP` through manufacturing settings. A DB constraint accepts only a nonempty, duplicate-free subset of `{IN_PROGRESS,READY,IN_SETUP}` that includes `IN_PROGRESS`. Reject lowercase strings and NULL; never admit `PENDING`, `ON_HOLD`, `COMPLETED` or `CANCELLED`. Missing, unreadable or malformed settings reject a **new** event. The MO still must be `in_progress`. Require an **explicit** work-order ID in each line of the new API; do not automatically select one. Each locked WO must belong to the same MO and organization, and have a non-NULL status allowed by the locked policy. Use NULL-safe comparisons. The current MO status transition problem belongs to #230; seed test WO status directly.
- Revoke all direct client write privileges on the dedicated policy table, with no client write policies, including for Org Admins. Only an audited, tightly scoped SECURITY DEFINER settings RPC may change the caller's own organization row after checking active Org Admin membership; it rejects any invalid array before writing, increments a monotonic policy version and records actor, org, before/after and version in an audit record within the transaction. An ordinary employee may read the effective policy only through a tenant-scoped read path, and cannot change it. Explicitly deny direct INSERT, UPDATE, DELETE and TRUNCATE by an authenticated Org Admin and by anon.
- **Settings concurrency:** after event-key serialization and the MO lock, a **new** event locks the policy row `FOR SHARE`, validates it, then locks the explicit WO; the settings RPC locks the same policy row `FOR UPDATE` before changing it. This orders the operations under READ COMMITTED: a policy tightening waits for an in-flight event to commit, or a later event sees the new policy. Store both exact allowed-status array and monotonically increasing version in the event receipt. An authorized identical replay reads its previous result without checking current policy, even if that policy has changed or its row is missing; membership and permission are still checked.
- **Replay order:** authenticate, check active same-org membership and exact permission even for a replay; acquire the transaction-scoped `(org_id,event_id)` serialization lock **before** the MO lock, lock the MO, then look up the receipt and compare the immutable fingerprint. Return the stored result for an identical completed event **before** new-event lifecycle, policy, WO, stage/WIP, reservation, stock or UoM checks. A changed request conflicts without effects. Replay must work after WIP close, reservation exhaustion or MO completion, while revoked permission must still deny it.

## Event identity and API

1. The client creates one stable non-null UUID event ID for the complete batch and retains it after response loss, retries and reloads. Each genuine second partial issue uses a new ID even on the same reservation. The server must not silently invent a fresh ID during retry.
2. Provide an explicit required event ID parameter on a new event-bearing RPC. The existing callable signatures `rpc_consume_reserved_materials_v2(uuid,uuid,jsonb)`, `rpc_consume_reserved_materials(uuid,jsonb)`, and `consume_materials_for_mo(uuid,uuid,jsonb[])` must reject **before writing** with a clear migration error, or be replaced so that no callable eventless write path remains. A four-argument overload alone leaves a bypass. Catalog-scan all granted wrappers and definer writers, including backflush; test each old signature with an authorized user. No silent client fallback to an old signature.
3. Require explicit item, reservation, warehouse, work-order, quantity and UoM for every line; exactly one explicit stage for the entire batch and a fixed `MANUAL` consumption type. Reject `BACKFLUSH`, `NEGATIVE`, missing and unknown keys, malformed or duplicate reservation IDs, quantity strings, nonpositive quantities and quantities beyond six decimal places. Do not resolve omitted identifiers from changing inventory state. Snapshot first-run resolved references and UoM factor; never recompute them on replay.
4. Fingerprint the validated normalized **raw request**, before any state-dependent lookup: organization, actor, MO, event ID, stage, consumption type, notes, and all ordered lines and their business fields. Normalize JSON object property order and numeric JSON values (e.g. `10` and `10.0` equivalent if both accepted); preserve line order. Changing a business field or the actor conflicts, while the same event ID in another organization remains independent. Never fingerprint values derived from current stock or reservation state on a retry.
5. Persist one immutable result and receipt with `UNIQUE (org_id,event_id)`, actor, fingerprint and links to all created consumption/stock effects **in the same transaction** as SLE/bin, reservation and stage-WIP effects. Prefer a private schema; explicitly `REVOKE ALL` on receipt and policy tables from `PUBLIC`, `anon`, `authenticated` (including baseline default grants), grant back only required tenant-scoped reads, and enable RLS if either is in an exposed schema. New RPCs/helpers must explicitly revoke default EXECUTE from PUBLIC and anon; authorize only needed roles. Privileged RPCs must fix search paths, check auth/org/permission explicitly and restrict EXECUTE. Audit any `service_role` use as trusted server-only; never expose its credentials to clients. Migration postflight checks effective grants, RLS, constraints and actual client write denial.
6. Serialize calls by a transaction-scoped lock keyed on `(org_id,event_id)` (e.g. a deterministic advisory hash; hash collisions can only serialize unrelated events), **before** locking any MO, then lock MO, policy row for a new event, explicit WO, reservations and products. Receipt uniqueness is an independent backstop; never ignore an unchecked `ON CONFLICT DO NOTHING`. After waiting, reread the committed receipt: identical request returns stored result, including if the concurrent request used a different MO; changed request conflicts; a rolled-back first transaction lets the waiter apply once. Raw `23505` is not a successful replay result. A multi-line failure must roll back every earlier line and receipt without swallowing per-line exceptions. Result counts reflect committed linked rows, not input length. A failed event leaves no receipt; the same ID may later succeed if conditions change.

Every **effect-writing function, including the new event-bearing RPC even if v2 becomes reject-only**, must preserve M190's exact-permission check and all of M191 Fix E: ordered lock of all MO reservation rows regardless of status (`ORDER BY id FOR NO KEY UPDATE`); product prefix resolved without raising; `wardah_lock_products_for_stock_write` before the line loop; `PRODUCT_NOT_PRELOCKED`; and per-line reservation re-lock `FOR NO KEY UPDATE`. Verify that the function owner may execute the product-lock helper. Do not reinstate the pre-M191 function. Choose the next migration number after checking `main`; Production needs separate authorization.

Revoke direct `material_consumption` INSERT from `authenticated` and `anon`, remove permissive INSERT policies and verify neither role can UPDATE, DELETE or TRUNCATE; audit all callable writers. Keep only necessary reads, maintain retired backflush and block commit if privileged write checks fail. RLS does not restrict a misconfigured SECURITY DEFINER function.
